# Chapter 24: **IP 주소를 관리하기 위한 서비스 파악하기**

### 24.1 관리형 접두사 목록이란?

<aside>

- 하나 이상의 IP 주소 범위(**CIDR 블록**)를 묶은 **집합**
- 보안 그룹 또는 라우팅 테이블의 규칙에서 참조 가능
</aside>

#### 왜 필요한가 — 문제 상황 예시

SSH 접속을 허용해야 할 IP가 4개 있다고 가정:

```
1.2.3.4/32
1.3.4.4/32
2.3.4.4/32
3.3.4.4/32
```

**접두사 목록 미사용 시** → 보안 그룹에 규칙 4개를 각각 추가해야 함

```
SSH TCP 22 1.2.3.4/32
SSH TCP 22 1.3.4.4/32
SSH TCP 22 2.3.4.4/32
SSH TCP 22 3.3.4.4/32
```

**접두사 목록 사용 시** → 4개 IP를 목록 하나로 묶고, 보안 그룹엔 목록을 참조하는 규칙 1개만 추가

```
관리형 접두사 목록
├── 1.2.3.4/32
├── 1.3.4.4/32
├── 2.3.4.4/32
└── 3.3.4.4/32

보안 그룹
└── SSH TCP 22 → 관리형 접두사 목록
```

#### IP 목록을 개별 관리할 때의 문제점

- 보안 그룹 규칙 수 증가
- 같은 IP 목록을 여러 보안 그룹에 **중복 등록**
- IP 변경 시 **모든 보안 그룹을 일일이 수정**해야 함
- 전체 허용 IP 파악 어려움, 누락·오입력 가능성
- 유지보수 비용 증가, 가독성 저하

#### 사용 전/후 비교

**사용 전**: 보안 그룹 A, B가 각각 IP 1~4를 개별 보유 → IP 변경 시 A, B 모두 수정

**사용 후**: 접두사 목록 하나를 A, B가 함께 참조 → 목록만 수정하면 양쪽에 일관되게 반영

### 24.2 접두사 목록의 두 종류

#### 24.2.1 고객 관리형 접두사 목록 (Customer-managed)

사용자가 직접 생성·관리하는 IP 집합. 다음이 가능:

- 생성, CIDR 항목 추가/수정/삭제
- 최대 항목 수(MaxEntries) 지정
- 다른 AWS 계정과 공유
- 보안 그룹/라우팅 테이블에서 참조

흐름:

```
사용자 → 고객 관리형 접두사 목록 생성 → CIDR 등록 → 보안 그룹/라우팅 테이블에서 참조
```

예시:

```
office-ssh-ips
1.2.3.4/32
1.3.4.4/32
2.3.4.4/32
3.3.4.4/32
```

#### 24.2.2 AWS 관리형 접두사 목록 (AWS-managed)

AWS가 자체 서비스의 IP 대역을 미리 관리해 제공. **사용자는 수정 불가**

대표 대상 서비스:

- CloudFront, DynamoDB, Ground Station, Route 53, S3, S3 Express One Zone, VPC Lattice

활용 예:

- CloudFront에서 오는 트래픽만 허용
- VPC 엔드포인트 통해 S3로 가는 트래픽 설정
- DynamoDB 주소로의 경로 설정
- AWS 서비스 IP 변경을 **자동으로 반영** (사용자가 추적할 필요 없음)

#### 비교표

| 구분 | 고객 관리형 | AWS 관리형 |
| --- | --- | --- |
| 생성 주체 | 사용자 | AWS |
| IP 관리 | 사용자가 직접 | AWS가 자동 |
| 수정 가능 여부 | 추가/수정/삭제 가능 | 불가 |
| 주요 대상 | 사내·협력사·관리자 IP | S3, CloudFront 등 |
| 보안 그룹/라우팅 테이블 사용 | 가능 | 가능 |
| 공유 | 다른 계정과 공유 가능 | AWS 제공 |
| 장점 | 조직 IP 정책 중앙 관리 | AWS IP 변경 신경 안 써도 됨 |

---

### 관리형 접두사 목록의 장점 (4가지)

1. **규칙 단순화**: IP 4개 → 규칙 4개 (기존) vs 접두사 목록 1개 → 규칙 1개 (개선)
2. **일관된 보안 정책**: 여러 보안 그룹이 같은 목록 참조 → 개별 수정 불필요
3. **유지보수성 향상**: 가독성↑, 중복↓, 누락 위험↓, 정책 중앙 관리
4. **확장성**: IP 증가 시 목록에 항목만 추가하면 됨 (단, `MaxEntries`는 보안 그룹 규칙 할당량에 영향 주므로 과도하게 크게 잡지 말 것)
5. **재사용성**: 하나의 목록을 보안 그룹 A/B/C, 라우팅 테이블 등 여러 리소스에서 동시 참조

### 24.3 실습: 고객 관리형 접두사 목록 활용

#### 전체 흐름

```
고객 관리형 접두사 목록 생성
  → 허용 IPv4 CIDR 등록
  → 보안 그룹 인바운드 규칙에 접두사 목록 지정
  → CloudFormation 스택 생성
  → VPC 콘솔에서 확인
  → 보안 그룹 적용 여부 확인
```

#### 24.3.1 CloudFormation — 접두사 목록 생성

yaml

```yaml
PrefixList:
  Type: AWS::EC2::PrefixList
  Properties:
    AddressFamily: IPv4
    Entries:
      - Cidr: 1.2.3.4/32
      - Cidr: 1.3.2.4/32
      - Cidr: 1.4.2.4/32
      - Cidr: 1.5.3.5/32
    MaxEntries: 4
    PrefixListName: !Sub ${SystemName}-${EnvName}-prefix
```

| 속성 | 설명 |
| --- | --- |
| `Type` | `AWS::EC2::PrefixList` — 고객 관리형 접두사 목록 생성 |
| `AddressFamily` | `IPv4` 또는 `IPv6` |
| `Entries` | 등록할 CIDR 목록. `/32`는 IP 1개만 정확히 지정 (예: `1.2.3.4/32` = `1.2.3.4` 단일 주소), 더 넓은 범위도 가능 (예: `10.0.0.0/24` = `10.0.0.0`~`10.0.0.255`) |
| `MaxEntries` | 최대 등록 가능 항목 수. **현재 항목 수 이상**이어야 함. 보안 그룹 규칙 할당량과 관련되므로 필요 이상 크게 잡지 않기 |
| `PrefixListName` | 목록 이름. `!Sub`로 시스템명+환경명 조합 가능 (예: `gr-product-prefix`) |

#### 보안 그룹에 접두사 목록 연결

```yaml
SecurityGroupIngress:
  - IpProtocol: tcp
    FromPort: 22
    ToPort: 22
    SourcePrefixListId:
      Fn::ImportValue: !Sub ${EnvName}-prefix
```

- `IpProtocol: tcp` — SSH는 TCP 사용
- `FromPort/ToPort: 22` — SSH 포트
- `SourcePrefixListId` — 출발지로 개별 IP 대신 **접두사 목록**을 지정 → 규칙 1개로 여러 IP 허용

#### 스택 간 값 공유 (Export/Import)

접두사 목록과 보안 그룹을 **다른 스택**에서 생성하는 경우:

**접두사 목록 스택 (Export)**

```yaml
Outputs:
  PrefixListId:
    Value: !Ref PrefixList
    Export:
      Name: !Sub ${EnvName}-prefix
```

**보안 그룹 스택 (Import)**

```yaml
SourcePrefixListId:
  Fn::ImportValue: !Sub ${EnvName}-prefix
```

→ 네트워크 공통 리소스와 애플리케이션 보안 그룹을 스택 단위로 분리 가능

#### 24.3.2 콘솔에서 확인

1. VPC 콘솔 → **관리형 접두사 목록** 메뉴
2. 생성한 목록 선택 → 상세 정보 확인
3. 등록된 CIDR 항목 확인
4. **연결** 탭에서 목록을 사용 중인 리소스 확인 (예: `리소스 유형: Security Group`, `리소스 ID: sg-xxxxxxxx`)

상세 화면 확인 항목: 목록 ID, 이름, 주소 패밀리, 상태, 최대 항목 수, 현재 버전, CIDR 항목, 연결된 리소스, 공유·태그 정보

#### 보안 그룹 규칙 결과

```
유형: SSH
프로토콜: TCP
포트 범위: 22
소스: pl-xxxxxxxx   ← 개별 IP가 아닌 접두사 목록 ID
```

```
기존 방식:  IP 4개 → 규칙 4개
목록 방식:  IP 4개 → 목록 1개 → 규칙 1개
```

### 사용 시 고려사항 (5가지)

1. **CIDR 범위 최소화**: `0.0.0.0/0` 같은 과도하게 넓은 범위 지양 → 최소 권한 원칙 (권장: `1.2.3.4/32`)
2. **MaxEntries 설정**: 현재 등록 수보다 작게 설정 불가, 과도하게 크면 보안 그룹 규칙 할당량 낭비
3. **변경 관리**: 하나의 목록이 여러 보안 그룹·라우팅 테이블에서 쓰이므로, 변경 전 연결된 리소스·삭제 대상 IP 사용 여부·신규 IP 신뢰성·서비스 차단 가능성을 확인
4. **명확한 이름 사용**: 목적이 드러나는 이름 (`production-admin-ssh-ips`, `partner-api-ips`, `cloudfront-origin-ips` 등)
5. **고객 관리형 vs AWS 관리형 구분**: 조직 IP는 고객 관리형, AWS 서비스 IP는 AWS 관리형 사용 (AWS가 IP 변경을 자동 추적해줌)
