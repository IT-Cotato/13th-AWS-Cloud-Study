# **Chapter 21. 모니터링 및 로깅 서비스 파악하기**

## **21.1 모니터링 및 로깅 서비스, Amazon CloudWatch란?**

> AWS 리소스·애플리케이션 상태를 **실시간 감시**하는 모니터링 서비스.
> 

> 
> 지표를 감시해 알림을 보내거나 임계값을 위반한 경우 모니터링 중인 리소스를 자동으로 변경하는 **경보**를 생성할 수 있다.
> 
> 예를 들어 경보는 인스턴스 중지, auto scaling 및 Amazon SNS 작업 시작, 종료 등으로 구성할 수 있다.
> 

!스크린샷 2026-07-18 오후 9.22.35.png

CloudWatch의 수집 대상 3가지:

| 항목 | 설명 |
| --- | --- |
| 메트릭(Metric) | CPU 사용률, 네트워크 트래픽 등 시계열 수치 데이터 |
| 로그(Log) | 시스템/애플리케이션 발생 기록 |
| 이벤트(Event) | 특정 시점의 상태 변화·작업 기록 |

그래픽 인터페이스를 통해 로그를 분석하고, 알람을 생성하고, 시스템 상태에 대한 통찰력을 빠르게 얻는 데에도 도움이 된다.

## **21.2 Amazon CloudWatch 살펴보기**

**핵심 기능 4가지**

**[메트릭 수집·시각화]**

모든 AWS 서비스는 자동으로 CloudWatch에 지표를 전송한다. 
사용자는 더욱 자세한 모니터링을 위해 비즈니스 관련 지표를 사용자 지정된 방식으로 업로드할 수도 있다.

**[임계값 기반 경보(Alarm) 생성]**

CloudWatch를 사용하면 측정 항목이 지정된 임계값을 초과할 때 자동으로 작업을 트리거하는 알람을 만들 수 있다.

- 알림 보내기(Amazon SNS와 통합 – Simple Notification Service)
- Lambda 함수를 실행.
- EC2 인스턴스를 시작, 중지 또는 다시 시작.
- 자동 확장 또는 축소를 구현하려면 자동 크기 조정 정책을 실행.

**[로그 수집·저장·검색]**

CloudWatch Logs는 애플리케이션, 시스템 및 AWS 서비스에서 생성된 로그 데이터를 캡처, 저장하고 액세스한다. **CloudWatch Logs 인사이트**SQL과 유사한 쿼리 구문을 사용하면 로그 데이터를 빠르게 분석하여 오류, 성능 병목 현상 또는 보안 문제를 찾는 데 도움이 된다.

**[SNS 등 타 서비스 연동 알림]**

## **21.2.1 메트릭**

> 
> 
> 
> CloudWatch Metrics는 AWS 리소스나 사용자 정의 지표를 시간 단위로 수집, 저장하는 기능.
> 

**표준 지표 (Standard Metrics)**

- AWS가 기본 제공/관리하는 메트릭.
- EC2, RDS 등 주요 서비스는 기본적으로 5분 간격 또는 1분 간격으로 무료로 제공됨.

**커스텀 지표(Custom Metric)**

- 기본 수집 항목 외에 직접 원하는 데이터포인트를 생성하여 CloudWatch로 전달 가능.

예를 들어 EC2의 CPU, 네트워크, Disk I/O 등은 기본 수집 가능하지만 EC2의 메모리 사용량을 커스텀 지표를 통해 수집 가능.

**고해상도 지표(high-resolution metrics)**

- 1초 간격 또는 10초 간격으로 수집되는 고해상도 지표.

사용자가 직접 생성해야 하며 별도 요금이 부과된다.

## **21.2.2 경보 (CloudWatch Alarm)**

> CloudWatch Alarm은 특정 지표의 조건 감시 및 알림 기능으로, 생성한 경보 개수 및 해상도에 따라 요금이 부과된다.
> 

**전형적 흐름**

```
EC2 CPU 메트릭 수집 → 임계값 비교 → 경보 상태 전환 → SNS 호출 → 관리자 이메일
```

**주요 구성 요소**

| 요소 | 의미 |
| --- | --- |
| MetricName | 감시할 메트릭 이름 |
| Namespace | 메트릭이 속한 AWS 서비스 |
| Statistic | 평균/합계/최댓값 등 계산 방식 |
| Period | 1회 평가 시간 간격 |
| Threshold | 경보 발생 기준값 |
| EvaluationPeriods | 조건 연속 충족 횟수 |
| ComparisonOperator | 비교 방식 |
| AlarmActions / OKActions | 경보 발생 시 / 정상 복귀 시 실행할 작업 |
| Dimensions | 감시할 구체적 리소스 지정 |
| TreatMissingData | 데이터 없을 때 처리 방식 |

**경보 상태 3가지**

- `OK` : 임계값 위반 안 함
- `ALARM` : 임계값 위반
- `INSUFFICIENT_DATA` : 평가용 데이터 부족

## 21.2.3 로그 (CloudWatch Logs)

> CloudWatch Logs는 시스템, 애플리케이션, AWS 서비스에서 발생한 로그를 수집하고 관리하는 기능이다.
> 

**구조 (계층형)**

```
로그 그룹(Log Group)
 └─ 로그 스트림(Log Stream)
     └─ 개별 로그 이벤트
```

**로그 그룹**

같은 목적/서비스 로그 묶음.

대상의 이름을 의미한다. 직접 지을 수도 있지만, 보통은 애플리케이션을 나타내는 이름으로 짓는다.

**로그 스트림**

애플리케이션 안의 로그 인스턴스나 특정한 로그파일 등을 의미한다.

**[로그 클래스] (2025.08 시점 요금)**

| 클래스 | 특징 | 요금 |
| --- | --- | --- |
| Standard | 자주 조회하는 로그 | $0.76/GB |
| Infrequent Access | 조회 빈도 낮은 로그 | $0.38/GB |

**보존 기간**

- 1일 ~ 10년, 또는 만료 없음 설정 가능
- 자동 삭제로 저장 비용 절감

**로그를 보낼 수 있는 곳**

```
◦ S3
◦ Kinesis Data Streams
◦ Kinesis Data Firehose
◦ AWS Lambda
◦ OpenSearch
```

- 로그는 기본적으로 암호화되며, 원한다면 KMS를 이용해 암호화 할 수 도 있다.

## **21.3 Amazon CloudWatch 활용하기**

**전체 흐름**

```
EC2 인스턴스 → CPUUtilization 메트릭 → CloudWatch Alarm → SNS Topic → 구독자 이메일
```

**CloudFormation 스택 생성 순서**

```
VPC.yml → IAM.yml → Security_Group.yml → EC2.yml → SNS.yml → CloudWatch_Alarms.yml
```

**1) SNS 토픽 생성**

```yaml
Resources:
  MySNSTopic:
    Type: AWS::SNS::Topic
    Properties:
      TopicName: !Sub ${SystemName}-${EnvName}-sns
      Subscription:
        - Endpoint: 알림받을이메일
          Protocol: email
```

- 스택 생성 후 인증 메일에서 **Confirm subscription** 클릭해야 구독 활성화
- 콘솔 구독 상태가 "확인됨"이어야 정상

**2) CloudWatch Alarm 생성**

```yaml
Resources:
  C2CPUUtilizationAlarm:
    Type: AWS::CloudWatch::Alarm
    Properties:
      AlarmActions: [Fn::ImportValue: !Sub ${EnvName}-sns]
      OKActions: [Fn::ImportValue: !Sub ${EnvName}-sns]
      MetricName: CPUUtilization
      Namespace: AWS/EC2
      Statistic: Average
      Period: 60
      EvaluationPeriods: 2
      Threshold: 40
      TreatMissingData: breaching
      ComparisonOperator: GreaterThanOrEqualToThreshold
      Dimensions:
        - Name: InstanceId
          Value: !Ref Ec2InstanceId
```

→ **60초 평균 CPU ≥ 40%가 2회 연속** 감지되면 ALARM → SNS 이메일 발송 (OK 복귀 시도 알림)
→ `TreatMissingData: breaching` = 데이터 없어도 위반으로 간주

**3) 부하 테스트**

```bash
sudo amazon-linux-extrasinstall epel -ysudo yuminstall stress -ysudo stress --cpu1 --timeout600
```

- CPU 1개, 600초 동안 최대 부하
- AWS Fault Injection Service로도 부하 시험 가능
