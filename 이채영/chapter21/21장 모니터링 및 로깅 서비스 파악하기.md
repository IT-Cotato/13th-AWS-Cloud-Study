# 모니터링 및 로깅 서비스, 아마존 클라우드워치 살펴보기

- 메트릭 : 클라우드워치 메트릭(Metric)으로 표현할 수 있으며, 지표를 의미한다.
- 아마존 EC2 혹은 아마존 RDS와 같은 감시 대상으로부터 취득하는 데이터를 정리해놓은 것

## 모니터링 및 로깅을 위한 서비스, 메트릭

- AWS 내에서 관리할 수 있는 범위의 정보는 표준 지표로 수집할 수 있다.
1. EC2 인스턴스를 선택해 [모니터링] 클릭
2. CPU 사용률과 네트워크 트래픽 정보를 확인할 수 있다.

()

- 아마존 RDS에서는 EC2 인스턴스와는 다르게 메모리 및 디스크 사용량과 같은 정보가 포함된다.
- 각 서비스마다 수집하는 정보가 다른 이유는 ‘AWS 내에서 관리할 수 있는 범위의 정보’가 각 서비스마다 다르기 때문이다.
- 표준 지표 : ‘AWS 내에서 관리할 수 있는 범위의 정보’ 수집
- 맞춤형 지표 : 표준 지표로 수집되지 않은 정보를 수집할 때 사용자가 직접 커스텀해 지표를 만들 수 있다.
- EC2 인스턴스의 표준 지표에는 디스크 사용률과 메모리, OS 이상의 정보는 수집하지 않기 때문에 맞춤형 지표를 이용해 수집해야 한다.

## 모니터링 및 로깅 서비스, 경보

- 아마존 EC2나 RDS와 같은 서비스에 대해 실시간 모니터링을 수행하고, 수집된 데이터를 바탕으로 향후 서비스 운영 방침을 결정할 수 있다.
- 하지만 매번 콘솔 화면으로 들어가서 확인 절차를 거치고 그에 따른 운영 방침을 결정하는 것은 번거로움
- AWS에서는 이런 문제를 해결하는 클라우드워치경보(CloudWatch Alarm) 서비스를 제공

()

- ex. 표준 지표를 기반으로 EC2 인스턴스를 실시간으로 모니터링하는 환경이 있다.
- 이 환경에서 EC2 인스턴스의 CPU 사용률이 70%를 넘기면 경보를 발생시키고, 아마존 SNS를 통해 관리자에게 알림을 보낼 수 있도록 설정할 수 있다.
- 이런 경보를 통해 사용자는 직접 콘솔 화면에 들어가지 않아도 되며, 지정된 알람을 받아 향후 서비스 운영 방침을 결정할 수 있다.

## 모니터링 및 로깅 서비스, 로그

- 아마존 클라우드워치에서는 시스템, 애플리케이션, AWS 서비스의 로그를 중앙에서 관리하는 로그 그룹을 제공하고 있다.
- 사용자는 이런 로그 그룹을 통해 특정 오류 코드를 확인하고 트러블슈팅과 분석을 수행
- 로그를 관리하거나 분석 작업에 걸리는 시간을 최소화할 수 있다.
1. 아마존 클라우드워치 콘솔 화면에서 [로그 그룹] 선택
2. 로그 그룹의 리스트 확인
- 사용자가 직접 로그 그룹을 생성해 관리할 수도 있으며, 상황에 따라 로그 그룹이 자동으로 생성되는 경우도 있다.
1. 로그 그룹 리스트 중 하나를 클릭하면 [로그 스트림]에서 보존된 로그 확인 가능

()

- 이런 로그 그룹은 요금이 발생하는데, 아마존 S3와 동일하게 클래스 선택 가능

| 로그 클래스 | 요금 | 비고 |
| --- | --- | --- |
| Standard | USD 0.76 | GB당 발생 요금 |
| Infrequent Access | USD 0.38 | GB당 발생 요금 |

(2025.08 기준)

- 보존 설정을 통해 일정 시간이 지나면 로그를 자동으로 삭제하고 요금을 최소한으로 줄일 수 있다.
- 보존 설정은 짧게는 1일, 길게는 10년 혹은 만기 없음을 통해 로그가 삭제되지 않도록 설정할 수 있다.

## 모니터링 및 로깅을 위한 서비스, 메트릭을 취득할 수 있는 서비스

- 아마존 클라우드워치는 아마존 EC2와 아마존 RDS 이외에도 다양한 서비스에 대한 메트릭을 제공한다.

()

- AWS 앰플리파이, 아마존 API 게이트웨이, AWS 백업, 아마존 클라우드프론트를 포함해 다양한 서비스에 대한 메트릭을 제공하고 있다.
- 구축하고자 하는 환경에서 어떠한 서비스를 이용할지 결정하고, 해당 서비스가 어떠한 메트릭을 취득하는지 파악해 안정적으로 구축한 환경을 운영할 수 있도록 하자.

# 아마존 클라우드워치 활용하기

- 아마존 클라우드워치에서 경보 기능을 활용해 EC2 인스턴스의 CPU 사용률이 40%를 넘기면 지정한 이메일로 통지하도록 하자.

## 클라우드워치 경보를 활용해 이메일 통지해보기

> VPC.yml → IAM.yml → Security_Group.yml → EC2.yml → SNS.yml → CloudWatch_Alarms.yml 순서로 클라우드포메이션 스택을 생성해야 한다.
>

https://github.com/classmethodjaewook/aws-developer/tree/main/chapter21

1. SNS 토픽을 생성하고, 이메일을 인증한다.

```yaml
# SNS.yml

Resources:
  MySNSTopic:
    Type: AWS::SNS::Topic # 이메일로 통지를 받는 데 아마존 SNS 사용
    Properties:
      TopicName: !Sub ${SystemName}-${EnvName}-sns
      Subscription: # 이메일 인증 필요
        - Endpoint: # 통지 받을 이메일 입력
          Protocol: email
```

1. 스택을 생성한 뒤에 지정한 이메일 계정으로 AWS Notifications로부터 받은 이메일을 확인할 수 있다.
- 메일을 열어 [Confirm subscription]을 클릭하면 이메일 인증이 완료되었다는 [Subscription confirmed!] 팝업 창이 뜬다.

1. 클라우드워치 경보 생성
- 어떠한 리소스를 기준으로 경보를 발생시킬지 결정해야 한다.
- 이번에는 EC2 인스턴스의 CPU를 모니터링하고 경보를 발생시킬 예정
- 대상이 되는 EC2 인스턴스를 특정 짓는 방법은 EC2 인스턴스의 ID를 바탕으로 한다.

```yaml
# CloudWatch_Alarms.yml

Parameters:
  Ec2InstanceId: # EC2 인스턴스 ID 선택
    Description: Ec2 InstanceId
    Type: AWS::EC2::Instance::Id
Resources:
  C2CPUUtilizationAlarm:
    Type: AWS::CloudWatch::Alarm
    Properties:
      AlarmActions: # 경보가 발생했을 때 이메일을 통지하도록 설정
        - Fn::ImportValue: !Sub ${EnvName}-sns
      AlarmName: !Sub ${SystemName}-${EnvName}-Alarms
      MetricName: CPUUtilization # CPU 사용률 모니터링하고 경보하도록
      Namespace: AWS/EC2
      Statistic: Average # 평균값 계산
      Period: 60 # 모니터링 간격 (60초)
      EvaluationPeriods: 2 # 다음 60초 동안도 CPU 평균 사용률이 40%를 넘는다면 데이터 포인트 수가 증가해 합산 데이터 포인트 수가 [2]가 되어, 경보가 발생하고 이메일로 통지 실시
      Threshold: 40
      TreatMissingData: breaching
      OKActions:
        - Fn::ImportValue: !Sub ${EnvName}-sns
      ComparisonOperator: GreaterThanOrEqualToThreshold # 임곗값보다 크거나 임곗값과 같음
      Dimensions: # 모니터링할 리소스를 어떻게 지정할지 정한다.
        - Name: InstanceId
          Value: !Ref Ec2InstanceId
```

- 현재 생성한 EC2 인스턴스는 최저 스펙으로 생성된 서버이기 때문에 곧 바로 경보가 발생할 수도 있지만, 경보가 발생하지 않는다면 stress를 사용해 강제로 CPU 사용률을 올려 경보를 받아볼 수도 있다.

!image.png

```bash
# stress 설치 명령어

sudo amazon-linux-extras install epel -y
sudo yum install stress -y
sudo stress --cpu 1 --timeout 600
```

- EC2 인스턴스는 세션 관리자로 접속해 stress를 설치하고 600초 동안 1개의 CPU를 최대한 사용하도록 한다.
- 이 명령어로 EC2 인스턴스의 CPU 사용률이 올라가게 되며 경보가 발생
