# Chapter 13. 컨테이너를 위한 백엔드 서비스 파악하기

## 13.1 컨테이너 서비스, 아마존 ECS란?

아마존 ECS(Elastic Container Service)는 AWS에서 도커 컨테이너를 배포하고 운영·관리하는 완전 관리형 컨테이너 서비스. ECS 구성을 이해하기에 앞서 먼저 도커와 컨테이너를 학습.

### 도커와 환경 불일치

도커는 **환경 불일치(Environment Disparity)** 를 해결하는 오픈 소스 프로젝트.

- 환경 불일치: 윈도우에서는 정상 동작하지만 우분투 등 다른 OS에서는 동작하지 않는 상태
- 도커는 다른 컴퓨터에서도 같은 개발 환경을 구성할 수 있어 환경 불일치를 해결

도커에서 같은 개발 환경을 구성하는 방법은 두 가지.

- 도커파일(Dockerfile)을 만드는 방법
- 도커허브(DockerHub)에서 도커 이미지를 내려받는 방법

### 도커파일 예시

```docker
FROM nginx:latest
MAINTAINER "kim.jaewook"
COPY ./index.html /usr/share/nginx/html/index.html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

도커파일은 엔진엑스(Nginx) 환경을 구성하는 설정 파일. 작성 시 파일명은 반드시 `Dockerfile` 혹은 `dockerfile`로 설정.

| 명령어 | 설명 |
| --- | --- |
| `FROM` | 베이스 이미지 지정 (여기서는 엔진엑스 최신 버전) |
| `MAINTAINER` | 도커파일 작성자/수정자 이름 지정 |
| `COPY` | 호스트 파일을 지정된 디렉터리에 복사 (로컬 `./index.html` → `/usr/share/nginx/html/`) |
| `EXPOSE` | 컨테이너가 노출할 포트 지정 |
| `CMD` | 컨테이너 시작 시 실행될 기본 명령 지정 (엔진엑스 시작 명령) |

설정한 도커파일로 하나의 컨테이너를 구성하면 같은 개발 환경을 어떤 OS에서도 문제없이 사용 가능.

### 컨테이너 구성 과정

```
사용자 → 서버(도커 설치) → 도커파일 작성 → 빌드(컨테이너) → 다른 서버에 도커 설치 후 동일 환경 구성
```

1. 로컬 환경 혹은 개발 서버에 도커 설치
2. 구성하고자 하는 환경을 바탕으로 도커파일 작성
3. 작성한 도커파일을 다른 서버로 업로드하고, 그 서버에도 도커 설치
4. 업로드된 도커파일을 빌드해 같은 개발 환경 구성

이렇게 구성한 가상의 개발 환경이 **컨테이너(Container)**. 직접 도커파일을 만드는 방법 외에 도커허브에서 다른 사람이 만든 도커파일을 다운로드해 구성하는 방법도 존재.

### 도커허브

도커허브는 자신이 만든 도커파일을 업로드하거나 다른 업로더가 만든 도커파일을 내려받을 수 있는 **공유 플랫폼**. 사용자들은 서로의 도커 이미지를 공유·재사용함으로써 개발 환경을 효율적으로 관리.

> EC2 인스턴스의 커뮤니티 AMI 또한 사용자가 만든 AMI를 업로드·공유할 수 있다는 점에서 비슷한 목적을 가짐.
>

### 컨테이너의 개념과 생성 흐름

컨테이너는 호스트 OS에 컨테이너 전용 영역을 만들고 그 위에 애플리케이션을 실행하는 메커니즘.

```
① 도커파일 → ② 빌드 → ③ 도커 이미지 → ④ 실행 → ⑤ 컨테이너
```

1. **도커파일**을 만들고
2. **빌드**하면
3. **도커 이미지**가 됨 (도커파일 내용이 포함된 하나의 정적 상태)
4. 도커 이미지를 **실행**하면 정적 → 동적 상태로 변하며
5. **컨테이너**가 됨

### 컨테이너의 독립성

컨테이너는 **독립적**. 하나의 서버에 복수의 컨테이너를 만들어 관리·서비스 가능.

> 예: Ubuntu OS용 컨테이너, 엔진엑스 환경 컨테이너, PHP 개발 환경 컨테이너 등을 각각 만들어 운영
>

이런 특징으로 컨테이너는 새 프로젝트를 진행할 때마다 EC2 인스턴스를 생성하거나 물리 서버를 구입해 설정할 필요가 없음.

### 도커 생명주기 흐름

```
도커허브
  │ docker pull
  ▼
서버 ──docker create──► [생성] ──docker start──► [실행] ──docker rm──► [제거 단계]
  └────────── docker run ──────────────────────────┘
                          [실행] ──docker stop──► [정지 단계]
                          [정지 단계] ──docker start──► [실행]
                          [실행] ──docker pause──► [일시중지]
                          [일시중지] ──docker unpause──► [실행]
```

| 명령어 | 동작 |
| --- | --- |
| `docker pull` | 도커허브에서 도커 **이미지만** 다운로드 (정적 상태) |
| `docker create` | 이미지를 컨테이너화(생성) |
| `docker start` | 생성된 컨테이너 시작 |
| `docker run` | 이미지 다운로드 후 곧바로 컨테이너 시작 (실행마다 컨테이너 생성) |
| `docker stop` | 컨테이너 중지 |
| `docker pause` | 컨테이너 내부 프로세스 일시 정지 |
| `docker unpause` | 일시정지 컨테이너 재시작 |
| `docker rm` | 컨테이너 삭제 |
| `docker rmi` | 도커 이미지 삭제 |

> ⚠️ `docker run`은 실행할 때마다 컨테이너를 생성하므로, 컨테이너화가 필요할 때에만 실행하는 것이 좋음.
>

## 13.2 컨테이너 서비스, 아마존 ECS 살펴보기

앞서 도커와 컨테이너화 과정을 학습. 이번에는 그 내용을 바탕으로 아마존 ECS에서 이미지를 생성하고 컨테이너화가 이루어지는 과정을 학습.

### 13.2.1 컨테이너 서비스, 아마존 ECR 살펴보기

도커에서는 도커파일을 작성해 정적 도커 이미지를 생성. 아마존 ECS는 이 **정적 이미지를 보관하는 아마존 ECR(Elastic Container Registry)** 라는 서비스를 제공.

### ECR로 푸시하는 흐름

```
사용자 → 서버(도커) → 도커파일 ──빌드──► 도커 이미지 ──푸시──► 아마존 ECR
                          (도커파일 빌드하여 도커 이미지 생성)   (생성한 이미지를 ECR로 푸시)
```

1. 도커를 설치하고 도커파일을 작성해 정적 도커 이미지 생성
2. **AWS CLI**를 사용해 아마존 ECR로 푸시 작업 수행
3. 푸시된 정적 이미지는 아마존 ECR에서 관리

AWS는 ECR로 푸시하는 명령어를 ECR 콘솔 화면(OS별)에서 제공. 이를 통해 별도 환경 없이 AWS에서 중앙집중식으로 이미지 관리 가능.

### ECR 리포지토리 생성

정적 이미지를 푸시하려면 ECR **리포지토리**를 별도로 생성해야 함. ECR 콘솔 화면은 **프라이빗(Private)** 과 **퍼블릭(Public)** 으로 구분.

| 구분 | 설명 |
| --- | --- |
| 프라이빗 리포지토리 | IAM 혹은 특정 권한이 할당된 사용자만 사용 가능 |
| 퍼블릭 리포지토리 | 누구나 사용 가능 |

> ⚠️ 리포지토리 설정은 생성 후 재설정이 불가능하므로, 사용 목적을 명확히 생각해 설정해야 함.
>

### 13.2.2 컨테이너 서비스, 아마존 ECS 구성 요소

ECR에 푸시한 정적 이미지를 동적 이미지로 변환해 하나의 컨테이너로 사용하기 위해 아마존 ECS를 사용.

### 아마존 ECS 작업 정의 (Task Definition)

ECR 리포지토리에 생성한 정적 이미지를 사용하려면 ECS에서 **작업 정의**를 작성해야 함.

```
아마존 ECR ──(작업 정의에서 ECR 이미지를 사용)──► 작업 정의
```

작업 정의는 ECR 이미지를 비롯한 컨테이너의 전체적 구성을 정의하는 것으로, 어떤 컨테이너를 만들 것인지를 설정하는 작업.

**작업 정의 포함 항목**

- 작업 정의 이름
- 컨테이너 이름
- 사용할 이미지
- 사용할 포트 번호
- 환경 변수 설정
- 컨테이너에 연결할 볼륨
- 실행 역할
- 네트워크 모드

### 네트워크 모드

네트워크 모드는 **호스트, 브리지, awsvpc, 없음** 네 가지 중 선택.

### ① 호스트(Host) 모드

호스트의 ENI(Elastic Network Interface)를 사용해 컨테이너가 통신하는 모드.

```
[프라이빗 서브넷]
포트:8080 ──► ENI ──► 포트:8080 ──► 컨테이너   (호스트 8080 포트 사용)
포트:8080 ──► ENI(다른) ──► 포트:8080 ──► 컨테이너   (다른 ENI에서 8080 사용)
```

- 호스트에서 사용하는 포트가 곧 컨테이너 포트
- ENI를 **나누어** 컨테이너를 구성하면 같은 포트(8080)를 써도 문제없음
- 같은 ENI를 사용하면 포트 중복으로 문제 발생

> 💡 ENI는 가상 네트워크 인터페이스를 의미하며, 생성한 리소스에 연결되어 IP 주소를 부여.
>

```
[하나의 ENI 사용 시]
포트:8080 ──► ENI ──► 포트:8080 ──► 컨테이너  (8080 사용 중)
              └──► 포트:8081 ──► 컨테이너  (다른 8081 → 사용 가능)
              └──► 포트:8080 ──► ✕ 컨테이너  (이미 사용 중 → 불가)
```

- 하나의 ENI만 사용 시, 8080이 이미 쓰이고 있다면 8081처럼 다른 포트를 지정해야 함
- **호스트 모드에서는 부하 분산 구현이 불가능**. 컨테이너의 네트워크 네임스페이스가 호스트와 공유되어 컨테이너 포트가 호스트 포트로 직접 매핑되기 때문

### ② 브리지(Bridge) 모드

ENI와 컨테이너 사이에 **브리지 레이어**를 추가해, 호스트와 컨테이너를 다른 포트로 연결할 수 있도록 하는 모드.

```
[프라이빗 서브넷]
포트:8080 ──► ENI ──► [브리지] ──► 포트:8000 ──► 컨테이너
포트:8080 ──► ENI ──► [브리지] ──► 포트:8000 ──► 컨테이너
```

- 호스트와 컨테이너의 포트가 구분되어 **같은 포트로 여러 컨테이너를 가동** 가능
- 따라서 **로드 밸런서를 사용한 부하 분산** 가능

```
[탄력적 로드 밸런서]
탄력적 로드 밸런서 ──► ENI(포트:8080) ──► [브리지] ──► 포트:8000 ──► 컨테이너
                                    └──► [브리지] ──► 포트:8000 ──► 컨테이너
```

- 호스트 포트는 브리지의 **동적 매핑** 기능에 의해 별도 지정 가능
- 호스트 포트를 `0`으로 지정하면 컨테이너 인스턴스의 임시 포트 범위(32768~61000)에서 동적으로 매핑. 이를 **에페메랄 포트(Ephemeral Port, 32768-61000)** 라고 함
- 단, 포트를 무작위로 할당하면 제어가 어려우므로 사용에 주의 필요

### ③ awsvpc 모드

각 컨테이너마다 ENI를 생성해 대응하는 모드.

```
[프라이빗 서브넷]
호스트 ENI
포트:8080 ──► ENI ──► 포트:8000 ──► 컨테이너
포트:8080 ──► ENI ──► 포트:8000 ──► 컨테이너
```

- 생성된 ENI는 호스트와 **별도로** 생성되며, VPC 내에서 **자체 사설 IP**가 할당
- 각 컨테이너에 대해 보안 설정 구성 가능, 같은 호스트의 컨테이너로부터 통신 제한도 가능
- 더 유연한 설정이 가능한 모드
- **단점**: 생성 가능한 ENI 수에 제한이 있음

### ④ 없음(None) 모드

```
[프라이빗 서브넷]
ENI ──✕── 컨테이너
    ──✕── 컨테이너
```

- **포트 매핑 불가능**, **외부와의 연결도 차단**된 모드
- 로그 수집, 데이터 교환, 데이터베이스 등 네트워크 기능이 불필요할 때 사용

### 아마존 ECS 작업 (Task)

작업 정의를 통해 컨테이너를 설정했다면, **작업(task)** 을 통해 그 설정을 적용하고 컨테이너를 실행 가능.

```
아마존 ECR ──► 작업 정의 ──┬──► [컨테이너][컨테이너] = 작업
                          └──► [컨테이너] = 작업
```

- 작업은 작업 정의를 기반으로 시작한 컨테이너의 모음
- 단일 작업 내에서 여러 컨테이너 시작 가능. 엔진엑스와 마리아DB 같은 서비스를 하나의 작업 내에서 실행 가능

### 아마존 ECS 서비스 (Service)

```
아마존 ECR ──► 작업 정의 ┄┄► [ 작업 { 아마존 EC2 / AWS 파게이트 + 컨테이너·컨테이너 } ]
                                            └────────── 서비스 ──────────┘
```

서비스는 **작업을 관리**.

- 작업 중 하나가 실패하거나 중지되면, 설정한 필요 작업 수에 따라 **자동으로 새 작업 시작**
    - 예: 작업 수를 2로 설정 → 작업 수 2가 유지되도록 관리
- 서비스에서는 컨테이너의 **시작 유형(EC2 인스턴스 / 파게이트)** 선택 가능

| 시작 유형 | 설명 |
| --- | --- |
| EC2 인스턴스 | 앞서 살펴본 컴퓨팅 서비스 |
| 파게이트(Fargate) | 컨테이너를 서버리스로 실행. 사용자는 애플리케이션에만 집중하고 OS 관리·운용 보수 불필요. 필요 리소스를 자동 관리하고 실행 환경을 프로비저닝 |
- 서비스에서는 컨테이너에서 사용할 보안 그룹, VPC, 서브넷 등 선택 가능

### 아마존 ECS 클러스터 (Cluster)

클러스터는 서비스와 작업을 포함하는 **컨테이너 관리 및 배포를 위한 컴퓨팅 자원의 집합**.

```
┌──────────────────── 클러스터 ────────────────────┐
│ [아마존 EC2: 컨테이너·컨테이너 / 서비스]            │
│ [AWS 파게이트: 컨테이너·컨테이너 / 서비스]          │
└───────────────────────────────────────────────┘
```

- 클러스터는 여러 EC2 인스턴스나 파게이트 작업으로 구성. 이를 통해 여러 서비스 및 작업을 실행·관리 가능

## 13.3 아마존 ECS on 파게이트 생성해보기

이번 실습은 서버리스 서비스인 파게이트를 생성하고 관리하는 과정.

### 13.3.1 아마존 ECS on 파게이트 생성해보기 (CloudFormation)

### 01. 클라우드포메이션 yml 파일 구성

> **아마존 ECS on 파게이트 생성을 위한 yml 파일**
>
> - **파일 이름**: VPC.yml, IAM.yml, Security_Group.yml, EC2.yml, ECS.yml
> - **스택 생성 순서**: `VPC.yml → Security_Group.yml → EC2.yml → ECS.yml`

> 전체 코드는 깃허브 리포지토리 `[chapter13] → [ECS] → [chapter13.3.1-Create-ECS]` 폴더에서 확인 가능.
>

**구성할 컨테이너 환경**

퍼블릭 서브넷에 EC2 인스턴스 생성 → 도커 설치 → 엔진엑스 설치·기동 도커 이미지 생성 → ECR에 이미지 푸시 → 푸시한 이미지로 컨테이너 생성 → 사용자는 로드 밸런서를 통해 컨테이너에 접근.

```
                    인터넷
                      │
┌─────── VPC ─────────┼──────────────┐        사용자
│ [퍼블릭 서브넷]      │ [퍼블릭 서브넷]│          │
│  EC2 인스턴스(docker)│  탄력적 로드   │◄─────────┘
│        │            │  밸런서       │
│ 아마존 ECR ┄┄┄┄┄┄┄► │              │
│ [프라이빗 서브넷]    │ [프라이빗 서브넷]│
│  컨테이너 ◄──── AWS 파게이트 ────► 컨테이너 │
└─────────────────────────────────────┘
```

### 02. EC2 인스턴스 환경 구성

> **클라우드포메이션 스택 생성 순서**
>
> - **파일 이름**: VPC.yml, Security_Group.yml, EC2.yml
> - **생성 순서**: `VPC.yml → Security_Group.yml → EC2.yml`

VPC와 보안 그룹, EC2 인스턴스까지 순서대로 생성.

### 03. 도커 설치

```bash
sudo -i
yum install -y docker
systemctl start docker
docker images
# -> REPOSITORY  TAG  IMAGE ID  CREATED  SIZE
```

EC2 인스턴스에 접속해 위 명령어 입력. `docker images` 입력 시 REPOSITORY, TAG, IMAGE ID가 출력되면 설치·기동 성공.

### 04. index.html 파일 생성

```bash
mkdir dockerfile-folder
cd dockerfile-folder/

vi index.html
```

```html
<!doctype html>
<h1>hello ecs!</h1>
```

> 💡 vi에서는 `i`를 눌러 입력 모드로 변경하고, 입력 후 `esc` → `:wq`로 저장.
>

### 05. 도커파일 작성

```bash
vi dockerfile
```

```docker
FROM nginx:latest
MAINTAINER "kim.jaewook"
COPY ./index.html /usr/share/nginx/html/index.html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

`COPY` 명령으로 `index.html`을 `/usr/share/nginx/html` 경로에 복사해 접속 시 `hello ecs!`가 출력되도록 설정.

### 06. 도커 이미지 빌드

```bash
docker build -t ecs-nginx .
docker images
```

- 태그 명: `ecs-nginx`
- `.` : 도커파일의 경로
- 빌드 후 `docker images`로 생성된 이미지 확인

### 07. 도커 이미지 검증

```bash
docker create -i -t --name ecs-nginx-container -p 80:80 db68383e6d13
docker ps -a
docker start 7e67ceba1fe
```

- `p 80:80` : 호스트 포트 : 컨테이너 포트
- `db68383e6d13` : `docker images`로 확인한 nginx의 IMAGE ID
- `docker ps -a` 로 컨테이너 ID 확인 후 `docker start`로 실행

마지막으로 ① EC2 인스턴스 보안 그룹에 HTTP 포트를 열고, ② EC2 인스턴스 IP를 웹브라우저에 입력하면 `hello ecs!` 출력.

| 인바운드 규칙 | 유형 | 프로토콜 | 포트 | 소스 |
| --- | --- | --- | --- | --- |
| 기존 | SSH | TCP | 22 | 사용자 지정 |
| 추가 ① | HTTP | TCP | 80 | Anywhere (0.0.0.0/0) |

### 08. 아마존 ECR 리포지토리 생성

콘솔 진입 → ① `[Repositories]` 클릭 → ② `[리포지토리 생성]` 클릭 → ③ 리포지토리 이름 `ecs-nginx` 지정

### 09. ECR에 이미지 푸시

생성한 리포지토리 선택 → ① 리포지토리 선택 후 ② `[푸시 명령 보기]` 클릭 → AWS는 OS별 푸시 명령어 제공. 검증 단계에서 `docker build`를 이미 진행했으므로 ③ **1, 3, 4번 명령어**를 복사해 실행.

```bash
# 1. 인증 토큰 검색 및 Docker 클라이언트 인증
aws ecr get-login-password --region ap-northeast-2 | docker login --username AWS --password-stdin <계정>.dkr.ecr.ap-northeast-2.amazonaws.com

# 2. (이미 빌드했으므로 생략 가능)
docker build -t ecs-nginx .

# 3. 이미지에 태그 지정
docker tag ecs-nginx:latest <계정>.dkr.ecr.ap-northeast-2.amazonaws.com/ecs-nginx:latest

# 4. ECR 리포지토리로 푸시
docker push <계정>.dkr.ecr.ap-northeast-2.amazonaws.com/ecs-nginx:latest
```

푸시가 끝나면 리포지토리를 클릭해 생성한 이미지 확인 가능.

> 💡 명령어는 `sudo -i`로 루트 사용자로 전환 후 사용. 권한 문제 발생 시 3장에서 실시한 [AWS Configure 설정]을 EC2에도 실시.
>

### 10. ECS.yml — ECS를 위한 IAM 권한 생성 (ExecutionRole)

```yaml
ECSTaskExecutionRole:
    ManagedPolicyArns: # ❶
        - arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy
    Action: # ❷
        - ecr:CreateRepository
        - ecr:BatchImportUpstreamImage
```

- ❶ ECS 작업 실행에 필요한 주요 권한 `[AmazonECSTaskExecutionRolePolicy]`
- ❷ ECR 리포지토리 생성 권한 `[ecr:CreateRepository]`, 외부 이미지를 가져올 권한 `[ecr:BatchImportUpstreamImage]`

### 11. ECS.yml — ECS Exec을 위한 IAM 권한 생성 (TaskRole)

```yaml
TaskRole: # ❶
    Action:
        - "ssmmessages:CreateControlChannel"
        - "ssmmessages:CreateDataChannel"
        - "ssmmessages:OpenControlChannel"
        - "ssmmessages:OpenDataChannel"
```

- ❶ 아마존 **ECS Exec**(컨테이너에 로그인하는 기능)을 사용하기 위한 권한 생성

### 12. ECS.yml — 클러스터 생성 코드

```yaml
ECSCluster:
    Type: AWS::ecs::Cluster # ❶
    Properties:
        ClusterName: !Sub ${SystemName}-${EnvName}-cluster
```

- ❶ 클러스터는 별다른 설정 없이 타입과 클러스터 이름만 입력

### 13. ECS.yml — 서비스 생성 코드

```yaml
ECSService:
    Type: AWS::ecs::Service
    DependsOn: # ❶
        - InternetFacingALB
    Properties:
        ServiceName: !Sub ${SystemName}-${EnvName}-service # ❷
        Cluster: !Ref ECSCluster # ❸
        EnableExecuteCommand: true # ❹
        DesiredCount: 2 # ❺
        LaunchType: 파게이트 # ❻
        LoadBalancers: # ❼
            - ContainerName: !Sub ${SystemName}-task
              ContainerPort: 80
              TargetGroupArn: !Ref ALBTargetGroup
        TaskDefinition: !Ref ECSTaskDefinition # ❽
        NetworkConfiguration: # ❾
            AwsvpcConfiguration:
                SecurityGroups:
                    - Fn::ImportValue: !Sub ${EnvName}-파게이트-sg
                Subnets:
                    - Fn::ImportValue: !Sub ${EnvName}-web-subnet-1a
                    - Fn::ImportValue: !Sub ${EnvName}-web-subnet-1b
```

| 번호 | 설명 |
| --- | --- |
| ❶ | `[DependsOn]`으로 ECS보다 로드 밸런서가 먼저 생성되도록 설정 |
| ❷ | 서비스 이름 지정 |
| ❸ | 생성한 클러스터 지정 |
| ❹ | `EnableExecuteCommand: true` → Exec로 컨테이너 로그인 가능 |
| ❺ | 생성할 인스턴스 개수 (기본값 1) |
| ❻ | 파게이트 지정 |
| ❼ | 로드 밸런서·컨테이너 정보 입력 (컨테이너 포트는 작업 정의 포트와 동일해야 함) |
| ❽ | 작업 정의 지정 |
| ❾ | 컨테이너 보안 그룹과 서브넷 지정 |

### 14. ECS.yml — 작업 정의 코드

```yaml
ECSTaskDefinition:
    Type: AWS::ecs::TaskDefinition
    Properties:
        Family: !Sub ${SystemName}-${EnvName}-task # ❶
        ContainerDefinitions: # ❷
            - Name: !Sub ${SystemName}-task
              PortMappings:
                  - ContainerPort: 80
                    HostPort: 80
                    Protocol: tcp
              Image: !Sub ${AWS::AccountId}.dkr.ecr.${AWS::Region}.amazonaws.com/ecs-nginx:latest
        Cpu: 512 # ❸
        Memory: 2048
        ExecutionRoleArn: !GetAtt ECSTaskExecutionRole.Arn # ❹
        RequiresCompatibilities: # ❺
            - FARGATE
        NetworkMode: awsvpc # ❻
        TaskRoleArn: !GetAtt TaskRole.Arn # ❼
```

| 번호 | 설명 |
| --- | --- |
| ❶ | 작업 이름 지정 |
| ❷ | 컨테이너 포트·호스트 포트 지정, ECR에 푸시한 이미지 지정 |
| ❸ | 서버의 CPU·메모리 지정 |
| ❹ | 컨테이너 실행 역할 (작업의 모든 컨테이너에 이 역할의 접근 허가 부여) |
| ❺ | 파게이트 지정 |
| ❻ | 파게이트는 컨테이너만으로 서비스가 동작 → 컨테이너 본인이 ENI를 관리해야 하므로 `awsvpc` 모드 사용 |
| ❼ | 사용자를 대신해 작업 내 컨테이너가 AWS API를 호출할 수 있는 권한 설정 |

## 학습 마무리

이번 장에서는 컨테이너를 위한 백엔드 서비스인 아마존 ECS를 학습. 컨테이너의 개념, 컨테이너 생성용 소프트웨어 플랫폼인 도커, 컨테이너 생명주기, 아마존 ECS 구조를 파악.

### 핵심 요약

1. **아마존 ECS** 는 AWS에서 도커 컨테이너를 배포·운영·관리하는 완전 관리형 컨테이너 서비스.
2. **도커** 는 다른 컴퓨터에서도 같은 개발 환경을 구성해 환경 불일치를 해결하는 오픈 소스 프로젝트.
    - **도커파일**: 사용자가 직접 커스텀해 환경을 구성하는 방법
    - **도커허브**: 다른 사람이 만든 도커파일을 다운로드해 환경을 구성하는 방법
3. AWS에서는 **AWS CLI** 를 사용해 아마존 ECR로 푸시 작업을 수행, 정적 도커 이미지를 관리 가능.
4. **아마존 ECS** 는 작업 정의, 작업, 서비스, 클러스터 네 가지로 구성.
    - **작업 정의**: ECR 이미지를 비롯한 컨테이너의 전체적 구성을 정의 (어떤 컨테이너를 만들지 설정)
    - **작업**: 작업 정의 설정값을 적용하고 컨테이너를 실행
    - **서비스**: 작업을 관리. 작업이 실패/중지되면 설정한 필요 작업 수에 따라 자동으로 새 작업 시작
    - **클러스터**: 서비스와 작업을 포함하는 컨테이너 관리·배포용 컴퓨팅 자원의 집합 (여러 EC2 인스턴스·파게이트 작업으로 구성)
