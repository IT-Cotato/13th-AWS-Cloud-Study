# 1.1 AWS 입문하기

AWS란 무엇이고 어떻게 등장하게 되었는지, 현대 IT 분야에서의 역할과 AWS를 사용함에 있어 자주 사용되는 용어를 알아보자.

## 1.1.1 AWS란 무엇인가?

- **AWS**는 아마존에서 제공하는 클라우드 컴퓨팅으로, 인프라 환경을 구축하고 운영하는 데 필요한 다양한 온라인 서비스를 제공한다.
- 클라우드 컴퓨팅 유형에 따라 서비스를 제공하는 방법뿐 아니라 컴퓨팅 리소스, 스토리지, 데이터베이스, 네트워킹, 데이터 분석, 머신러닝 등 다양한 서비스를 선택하여 사용할 수 있다.
- AWS는 안정적이고 확장 가능한 글로벌 클라우드 인프라를 제공하기 위해 33개 지역에서 서비스를 운영하고 있다. 
   → 전 세계적으로 일관된 서비스 품질과 성능을 경험할 수 있다.

## 1.1.2 AWS, 어떻게 탄생했고 왜 많은 사람이 사용하는가?

- Amazon Web Service
- 원래 아마존 인터넷 쇼핑몰 운영에서 늘어나는 트래픽과 주문량을 감당할 목적으로 구축한 사내용 고성능의 인프라 시스템이었다.
    
    → 이를 전 세계 기업에 제공하는 클라우드 서비스로 확대
    

### 데이터센터에서 클라우드로의 전환

<img width="600" height="459" alt="Image" src="https://github.com/user-attachments/assets/4b474a5a-0a1e-4fe0-adf2-31cb76440bba" />

회사가 독립적으로 서버, 스토리지 및 네트워크 장비를 보유/관리하는 데이터센터를 운영하고 있었으나, 사용자 수가 증가함에 따라 데이터센터 운영에 한계가 발생했다.

### 데이터센터 운영의 한계

- 데이터센터 서버에 과부하가 걸리면, 새로운 서버를 추가해 부하를 분산하고 서비스의 가용성을 유지해야 했음
- 서버를 추가하는 데에는 많은 시간 비용이 소요
- 24시간 가동을 위한 많은 비용 및 냉각 시간/비용 필요

클라우드 컴퓨팅의 등장으로 기업들은 데이터센터에서 클라우드로의 이전을 고려하기 시작했다.

### AWS의 장점

- 종량과금제를 제공하여 필요한 만큼의 자원만 사용하고 지불
- 서버 부하에 따른 자유로운 확장과 민첩성을 제공 -> 기업이 신속하게 인프라를 확장, 축소할 수 있도록 지원
- AWS를 사용하면 인프라 비용을 절감, 비즈니스의 민첩성을 향상시킬 수 있음

이런 장점 덕분에 많은 기업이 데이터센터에서 클라우드로의 이전을 고려하게 되었다.

### AWS의 발전

- AWS는 2006년 Amazon S3를 시작으로 Amazon EC2라는 가상 클라우드 서비스를 출시
- 초기에는 기술적으로 숙련된 사용자를 대상으로 한 API 중심의 서비스
- 이후 서비스를 발전시켜 다양한 지역을 제공하고, AWS 관리 콘솔이라는 사용자 친화적인 UI 환경을 구축
- 최종적으로 아마존은 클라우드 컴퓨팅을 만들었으며, 당시 ‘클라우드’보다는 ‘웹 서비스’라는 단어가 주류였기에 아마존 웹 서비스라고 명명

### 서비스 지향 아키텍처 Service Oriented Architecture, SOA

- IT 자원을 물리적 장비가 아닌 호출 가능한 서비스로 정의하는 방식
- 아마존은 SOA를 구현
- 인프라를 쉽게 확장하고 관리할 수 있는 솔루션을 제공

> 네트워크 상에서의 부하 분산
> 
> - 다수의 중앙 처리 장치 또는 저장 장치와 같은 컴퓨터 자원에 작업을 나누어 처리하는 것

## 1.1.3 ‘AWS’와 ‘Amazon’ 접두사는 무얼 의미하는가?

서비스명 앞에 붙는 `AWS`와 `Amazon`에 따라 각각 유틸리티 서비스와 독립형 서비스로 나뉜다.

`AWS`가 붙은 서비스

- 유틸리티 서비스 → 혼자 사용하지 않고 다른 서비스와 함께 사용
- AWS 클라우드 포메이션 : 다른 AWS를 생성하고 관리하는 데 사용되는 유틸리티 서비스로 다른 AWS 서비스와 연결되어 효과적으로 동작하고 통합된다.

`Amazon`이 붙은 서비스

- 독립형 실행 서비스 → 사용자에게 단독 실행 가능한 서비스를 제공
- Amazon EC2 : 독립적 가상 컴퓨팅 리소스로 제공받으면서 AWS 이외의 다른 서비스와 함께 사용할 수도 있다.

> Elastic Load Balance와 같이 AWS, Amazon이 붙어 있지 않은 서비스도 있다.
>

# 1.2 AWS를 쓰려면 알아두면 유용한 클라우드 지식

AWS에서 자주 사용되는 용어를 알아보자.

## 1.2.1 온프레미스

온프레미스 On-premie는 조직이 자체적으로 IT 인프라를 소유하여 관리 및 운영하는 것이다.

- 물리적인 서버 등 IT 리소스 설치 필요, 많은 투자 비용/시간이 소요
- 자체 IT 인프라를 관리하는 데 설정, 구현, 업데이트, 오류 해결 등 유지 비용이 발생

## 1.2.2 클라우드

온프레미스의 불편함을 해소하고자 등장한 것이 클라우드 Cloud이다.

<img width="544" height="229" alt="Image" src="https://github.com/user-attachments/assets/b7c739f2-a3c5-4da1-b891-f36ee8f1a0b6" />

클라우드는 서버를 가상화하여 제3자가 사용자에게 저장소를 제공하는 형태이다.

- 물리적 IT 리소스를 설치할 필요 없음
- 온프레미스와 같이 인프라에서 발생하는 높은 초기 구축 비용과 유지보수, 확장성이 문제되지 않음
- 클라우드를 사용하면 단기간 내 서버 구축과 확장 가능
- 운영 효율성과 자원 활용성 증가

## 1.2.3 하이브리드 클라우드

하이브리드 클라우드 hybrid cloud는 기존의 온프레미스 환경과 클라우드 인프라의 이점을 결합한 최적의 인프라를 구축하는 방식이다.

<img width="496" height="228" alt="Image" src="https://github.com/user-attachments/assets/823793e8-a496-44d4-8950-83e26b428049" />

- 온프레미스의 데이터와 시스템 보안 및 기밀성을 유지하는 기능 포함
- 클라우드의 확장성과 유연성을 활용해 필요한 서비스를 구현

⇒ 비용과 시간 절약, 안정성과 성능 유지

하이브리드 클라우드는 유연성, 경제성, 신속성, 물리 서버의 보완성, 안정성을 갖추고 있어 현대적인 IT 인프라 구축에 중요한 전략이지만 한계가 있다.

- 온프레미스나 클라우드로 구축한 환경에 비해 시스템 구성이 복잡하므로 운영/관리가 어려움
- 온프레미스와 클라우드를 연결하는 별도의 네트워크망(전용성) 확보해야 함

## 1.2.4 서버리스

서버리스 :  개발 및 운영 과정에서 서버를 관리/배포할 필요 없이 원하는 기능을 구현하고 실행하는 클라우드 기반 서비스

- 주말에만 유저 수가 급증하는 서비스라면 일주일 내내 가동하는 서버는 비효율적일 수 있다.
    
    → 서버리스를 사용하면 필요한 시점에만 리소스를 활용해 비용 절약이 가능하고 개발 및 운영 과정에서 더 효율적이다.
    
<img width="666" height="291" alt="Image" src="https://github.com/user-attachments/assets/88a1eaea-5780-4f03-ac99-b412187904a5" />

서버리스 처리 : 애플리케이션에서 발생하는 다양한 이벤트에 대응하여 사전에 작성한 코드가 실행되는 것

- 사용자의 웹 애플리케이션 액세스, 파일 업로드, 데이터베이스에서 새로운 데이터의 입출력 등 이벤트가 발생하면 서버리스 함수 또는 스크립트가 작동
- 서버리스는 데이터베이스와 연계를 통해 데이터를 저장하거나 필요한 정보를 가져올 수 있음
    
    = 데이터 관리를 위한 별도 서버 구축 없이 효율적으로 데이터를 관리할 수 있음
    
- 데이터베이스 이외에도 다른 서비스와 연계 가능

## 1.2.5 리전

AWS의 글로벌 인프라 구성은 리전 region과 가용영역 availability zone, 에지 로케이션 edge location으로 구성된다.

리전 : 서비스가 제공되는 물리적인 국가/도시 단위의 지역

- AWS는 리전별로 제공하는 서비스가 다름
- 사용자에게 물리적인 거리를 좁혀 네트워크 속도를 향상시킴으로써 더 빠르고 안정적인 서비스를 제공
- 특정 지역에서 자연 재해로 인해 AWS 환경이 영향을 받는 경우를 대비해 리전을 운영
    
    → 대신 다른 지역의 서비스를 이용하고 서버를 유지하며 지속적인 서비스를 제공
    
- 각 리전에는 고유한 코드가 존재
    - 한국 서울 : [ap-northeast-2]

## 1.2.6 가용 영역

가용 영역 availability zone은 AWS 리전 내에 서버, 스토리지, 네트워크 장비를 저장하는 하나 이상의 물리적인 개별 데이터센터로 구성되며 각각 독립적으로 운영된다.

- AWS에서는 가용 영역에 데이터센터 발전기와 물리적인 보안 시설을 갖추고 있음
- 해당 가용 영역에 서버, 스토리지, 네트워크를 구성해 클라우드 환경을 구축할 수 있음
- 각 가용 영역은 물리적으로 떨어져 있어 독립적으로 운영됨
- 가용 영역은 리전 이름 뒤에 알파벳으로 구분
    - 서울 리전은 [ap-northeast-2a], [ap-northeast-2b], [ap-northeast-2c], [ap-northeast-2d] 4지 가용 영역 운영
- 서로 다른 물리적 위치에 있어 자연재해 등으로부터의 영향 최소화, 시스템 가동 중지 최소화
- 가용 영역은 네트워크를 통해 연결되어 한 가용 영역이 중단되더라도 다른 가용 영역을 통해 시스템을 계속할 수 있음

## 1.2.7 에지 로케이션

에지 로케이션은 오리진 서버의 콘텐츠를 서로 다른 지역에서 빠르게 접근할 수 있도록 만드는 캐시 서버의 모음이다.

<img width="706" height="439" alt="Image" src="https://github.com/user-attachments/assets/96ebf781-0574-4f0d-a1d9-bee9ea274f77" />

서로 다른 지역의 사용자 A, B, C가 서울에 있는 오리진 서버의 데이터에 접근한다면, 사용자 B, C는 느릴 것이다.

이를 해결하기 위해 사용자 B, C가 접근하고자 하는 데이터를 중간에서 **캐시**하면 된다.

에지 로케이션 : 사용자와 오리진 서버 사이에서 데이터를 캐시하는 역할

- 에지 로케이션에 캐시가 남아 있다면 사용자에게 캐시를 반환
- 캐시가 없다면 오리진 서버에서 데이터를 검색해 에지 로케이션에 캐시를 저장 후 사용자에게 반환

<img width="751" height="446" alt="Image" src="https://github.com/user-attachments/assets/74fe0b77-4c67-4351-a4c4-087d75e8b7c7" />

AWS는 에지 로케이션을 이용하여 아마존 클라우드프론트 Amazon CloudFront라는 CDN 서비스를 제공한다.

> CDN (Content Delivery Network) : 전 세계에 분산된 서버를 통해 사용자에게 가장 가까운 위치에서 웹 콘텐츠를 빠르게 전달하는 시스템
> 
- 사용자는 가장 가까운 에지 로케이션에서 콘텐츠를 빠르게 전송받을 수 있음
- 서버의 트래픽과 비용 절감할 수 있음

<img width="663" height="346" alt="Image" src="https://github.com/user-attachments/assets/8303a488-fce6-40a4-a53d-d1fbd93006e4" />

에지 로케이션에 캐시가 남아 있지 않는 경우 오리진 서버에서 콘텐츠를 취득해야 하는 문제를 해결하기 위해  오리진 서버와 에지 로케이션 사이에 **캐시 서버**를 둔다.

<img width="587" height="375" alt="Image" src="https://github.com/user-attachments/assets/5bd8307c-3d03-4db2-ae03-8633098f62d7" />

- 에지 로케이션은 용량 문제로 자주 접근하는 데이터만 캐시, 다른 캐시를 삭제해 최적화
- 캐시 서버는 더 큰 캐시 저장 가능
    
    → 오리진 서버 직접 접근 빈도 감소, 성능 저하를 줄일 수 있음
    

단점

- CDN을 위한 캐시 서버가 곳곳에 있지 않다면 한 곳에 서비스가 집중되어 트래픽 증가
- 캐시 서버를 운영하는 곳 중 한 곳이 중단되면 전체 시스템이 중단되는 단일 장애점 문제

## 1.2.8 가용성

가용성 :  리전 내 여러 상황이 발생해 시스템 장애가 나도 정상적으로 작동할 수 있는 정도

<img width="736" height="492" alt="Image" src="https://github.com/user-attachments/assets/10bbdbc6-e841-49ab-b740-0b76da31e853" />

시스템은 사용 가능한 시간이 길수록 가용성이 높고, 중지되는 시간이 길수록 가용성이 저하된다.

- 일반적으로 가용성은 일정 시간 동안의 가동 시간 비율로 정의
- 가용 가능한 가동률을 99%, 99.9%와 같이 백분율로 표시

AWS에서는 고가용성 high availability 용어도 자주 사용된다.

- 고가용성 : 시스템이나 서비스가 지속적으로 정상 운영되는 능력
- 고가용성의 시스템은 시스템 장애 발생 빈도가 극히 드묾
- 장애가 발생하더라도 빠르게 복구하여 서비스 중단 시간 최소화

## 1.2.9 신뢰성

신뢰성 : 가동 시간 동안 시스템이 예상대로 작동하고 중단되지 않는 정도

### 가용성과 신뢰성의 차이점

- 신뢰성은 시스템의 고장 간격 평가, 가용성은 시스템의 가동률로 평가
- 가용성을 평가할 때는 가동 시간과 함께 시스템 복구 시간도 고려되어야 함
    - 시스템이 1000시간 가동되었지만 고장이 발생해 복구 시간이 1000시간이었다면 가동률이 50%

## 1.2.10 내결함성

내결함성 fault tolerance : 시스템 장애가 발생하더라도 시스템 성능을 저하시키지 않고 서비스를 지속하게 하는 특성

- 시스템 장애 발생했을 때 우회하는 식으로 서비스를 지속시키며, 하위 시스템이나 중복 시스템을 작동시켜 유지

### 내결함성과 가용성의 차이점

- 가용성은 재해/장애가 발생하더라도 시스템이 사용자에게 서비스를 제공할 수 있는 상태를 유지하는 것
- 내결함성은 SLA(service level agreement)를 충족시키기 위해 시스템 성능을 저하시키지 않고 유지하는 것
    - SLA : 서비스의 품질에 대해 사용자와 서비스를 제공하는 사이의 합의를 나타내는 계약

- 즉, 서비스의 지속성을 우선시하는지, 서비스 품질을 우선시하는지의 차이

## 1.2.11 탄력성

탄력성 Elasticity : 시스템이 비즈니스 상황에 따라 트래픽이나 부하에 대응하여 유연하게 자동으로 조정하는 능력

- 트래픽이 1일 때는 서버를 적게 운영하다가 트래픽이 3으로 증가하면 서버 수를 증가시키도록 조정
- 탄력성은 변화에 빠르게 대응하여 시스템 성능 유지, 가용성을 높임

<img width="550" height="439" alt="Image" src="https://github.com/user-attachments/assets/efb471ae-3002-4ca4-9fff-1eb8e7cbc74e" />

AWS에서는 탄력성을 유지하기 위해 **오토 스케일링**을 제공한다.

- 오토 스케일링 : CPU 사용률, 네트워크 트래픽 등 미리 정의된 조건에 따라 서버를 추가/제거해 탄력성 유지

탄력성은 트래픽 조절, 불필요한 자원을 사용하지 않으므로 비용 최적화에 필수적인 기능이다.

## 1.2.12 확장성

확장성 Scalability : 비즈니스가 성장함에 따라 서버 용량이 한계에 도달할 때 인프라를 확장하는 것

서버를 확장하는 방법은 스케일업과 스케일아웃으로 나뉜다.

### **스케일업**

- 수직확장, 기존 서버의 성능을 향상시킴
- 서버 디스크 용량, 메모리, CPU 등을 업그레이드해 더 높은 사양을 갖추게 함
- 더 많은 리소스를 활용 가능 → 처리 능력 향상

### **스케일아웃**

- 수평확장, 기존 시스템과 비슷한 스펙의 서버를 추가
- 부하를 분산시켜 서버의 처리량을 늘림
- 사용자 증가나 트래픽 증가에 따른 서비스 확장에 사용됨

탄력성의 경우 기존 서버의 처리 능력을 향상시켜 트래픽을 부하 감당

확장성의 스케일아웃은 트래픽을 분산시키기 위해 서버 수를 늘림

AWS는 오토 스케일링을 통해 스케일업, 스케일아웃을 구현해 확장성을 확보한다.

## 1.2.13 비즈니스 연속성 계획

비즈니스 연속성 계획 BCP(business continuity plan) : 시스템 운영에 영향을 주는 재해와 장애를 방지하고 복구하는 대책

- AWS는 고가용성과 BCP인 운영 연속성을 위해 여러 리전을 운영
- 장애/재해 발생 시 적절한 조치를 취하고 재해 복구를 위한 DR 환경 구축, BCP 수립
- 한 리전에서 발생한 장애 회복을 위해 다른 리전에 백업 서버 및 데이터를 준비하는 계획을 수립하여 실행에 옮김
    
    → 서비스 중단 기간 최소화, 서비스 지속성 확보
