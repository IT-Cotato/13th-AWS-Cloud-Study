<h1>2. 부하 분산 서비스, 탄력적 로드 밸런서란?</h1>
<p>탄력적 로드 밸런서를 사용하면 사용자가 급증하더라도 적절하게 트래픽을 부하 분산할 수 있어 안정적으로 서버를 운영할 수 있다.</p>
<ul>
<li>탄력적 로드 밸런서는 웹 서버 앞에 배치되며, 사용자는 이 탄력적 로드 밸런서를 경유해 웹 사이트로 접근한다.</li>
<li>외부로 웹 서버를 공개할 필요가 없어지며, 사용자는 탄력적 로드 밸런서를 통해서만 웹 사이트를 접근할 수 있다.</li>
</ul>
<p>⇒ 서버의 보안을 강화하고, 사용자에게 안정적인 서비스 제공</p>
<h2>탄력적 로드 밸런서를 경유해 웹 서버에 접속하는 방법</h2>
<ul>
<li>탄력적 로드 밸런서는 퍼블릿 서브넷에 배치</li>
<li>탄력적 로드 밸런서에서는 이 서비스에 접근할 수 있는 DNS 이름을 별도로 제공</li>
<li>아마존 라우트53과 연동해 별도로 도메인 할당 가능</li>
<li>EC2 인스턴스에 도메인 할당하는 것이 아닌 탄력적 로드 밸런서에 도메인을 할당
<ul>
<li>ex) <a href="http://goldenrabbit.co.kr">goldenrabbit.co.kr</a></li>
</ul>
</li>
</ul>
<p>⇒ 사용자는 탄력적 로드 밸런서의 도메인을 사용해 웹사이트에 접근하면서도 사용자와 EC2 인스턴스 간 직접적인 접근을 완전히 차단할 수 있다.</p>
<ul>
<li>탄력적 로드 밸런서에서는 프라이빗 서브넷에 있는 EC2 인스턴스로 부하 분산을 시도</li>
<li>여러 가용 영역에 걸쳐 부하 분산 실시</li>
</ul>
<p>⇒ 하나의 가용 영역에 무너지더라도 다른 가용 영역에서 서비스를 지속할 수 있다.</p>
<h2>탄력적 로드 밸런서와 연동 가능한 서비스</h2>
<ul>
<li>아마존 EC2 오토스케일 → 서버 확장</li>
<li>아바존 ECS → 컨테이너 서비스</li>
<li>아마존 라우트53 →  도메인 라우팅</li>
<li>아마존 클라우드프론트 → 고속 콘텐츠 전송 지원</li>
<li>아마존 S3 서비스 → 접속 로그 기록 등</li>
</ul>

<p>탄력적 로드 밸런서에서는 ALB, NLB, GWLB 유형을 제공한다.</p>

<p><strong>애플리케이션 로드 밸런서 ALB</strong></p>
<ul>
<li>OSI 7계층 중 응용 계층을 사용해 부하 분산</li>

<p><strong>네트워크 로드 밸런서 NLB</strong></p>
<ul>
<li>4계층인 전송 계층을 사용해 부하 분산</li>
<li>TCP 또는 UDP 트래픽 라우팅</li>
</ul>
<p><strong>게이트웨이 로드 밸런서 GWLB</strong></p>
<ul>
<li>3계층인 네트워크 계층을 사용해 부하 분산</li>
<li>주로 타사 제품을 AWS로 마이그레이션할 때 사용
<ul>
<li>ex) 타사 제품을 AWS에 배포할 때 배포한 서버에 대해 VPC 피어링 또는 트랜짓 게이트웨이 등으로 네트워크를 연결해 라우팅을 수행한다.</li>
</ul>
</li>
<li>ALB NLB와 달리 웹 애플리케이션과 웹사이트 구축의 용도에는 부적합</li>
</ul>

<h2>3.1 로드 밸런서의 작동 방식</h2>
<p>로드 밸런서에서는 로드 밸런서를 퍼블릭 서브넷에 생성할지, 프라이빗 서브넷에 생성할지 선택할 수 있다.</p>
<h3>퍼블릭 서브넷 VS 프라이빗 서브넷에 생성</h3>
<ol>
<li>퍼블릭 서브넷에 로드 밸런서를 생성
<ul>
<li>외부 사용자에게 웹사이트를 공개해 웹 서비스를 제공하고 싶을 때</li>
</ul>
</li>
<li>프라이빗 서브넷에 로드 밸런서를 생성
<ul>
<li>사내에서만 특정 웹 서비스를 제공하고 싶을 때</li>
</ul>
</li>
</ol>
<p>로드 밸런서를 생성할 때 외부로 공개할지, 내부에서만 사용할지 설계 단계에서 반드시 고민해야 한다.</p>
<h3>로드 밸런서가 가용 영역을 구분하고 부하 분산을 실시하는 방법</h3>
<p>각 가용 영역에 로드 밸런서의 부하 분산을 도와주는 <strong>로드 밸런서 노드</strong>가 생성되기 때문이다.</p>
<p>로드 밸런서를 생성하면 선택한 서브넷에 로드 밸런서 노드가 생성되며, 이 로드 밸런서 노드로 인해 각 가용 영역을 구분지을 수 있고 부하 분산을 수행할 수 있다.</p>
<h3>보안 그룹 설정</h3>
<p>로드 밸런서는 EC2 인스턴스와 동일하게 보안 그룹을 설정할 수 있으며, 로드 밸런서로 접근하고자 하는 사용자를 제한할 수 있다.</p>
<ul>
<li>외부에 공개되는 웹사이트는 보안 그룹을 완전히 오픈
<ul>
<li>이후 EC2 인스턴스의 보안 그룹을 수정해 로드 밸런서의 접근만을 허용하면, 외부에서 접근하는 사용자는 로드 밸런서에만 접근할 수 있고, 직접적으로는 EC2 인스턴스에 접근할 수 없다.</li>
</ul>
</li>
<li>특정 사용자 그룹만 로드 밸런서에 접근하도록 제한하고자 하는 경우 보안 그룹 수정
<ul>
<li>EC2 인스턴스에는 개발자, 관리자 등 특정 그룹만 접근하도록 보안 그룹을 설정해 보안성 높임</li>
</ul>
</li>
</ul>
<h2>3.2 로드 밸런서의 대상 그룹과 리스너</h2>
<h3>대상 그룹</h3>
<p>로드 밸런서 노드는 가용 영역을 구분하는 용도로 생성되는 것이며, 부하 분산을 할 EC2 인스턴스를 선택할 수 없다.</p>
<ul>
<li>대상 그룹은 로드 밸런서 노드와 EC2 인스턴스 사이의 중간 다리 역할</li>
<li>부하 분산을 시도할 EC2 인스턴스를 등록하고 관리</li>
<li>로드 밸런서는 로드 밸런서 노드를 통해 가용 영역을 구분하고, 대상 그룹을 통해 부하 분산을 수행하고자 하는 EC2 인스턴스를 구분할 수 있다.
<ul>
<li>대상 그룹은 n개로 나눠 생성</li>
<li>EC2 인스턴스의 역할에 따라 대상 그룹을 구분하는 것이 바람직
<ul>
<li>ex) 하나의 대상 그룹에는 웹 서비스를 제공하는 EC2 인스턴스를 등록, 또 하나의 대상 그룹에는 API를 처리하는 EC2 인스턴스 등록</li>
</ul>
</li>
</ul>
</li>
</ul>
<p>

<img width="584" height="371" alt="Image" src="https://github.com/user-attachments/assets/0262dc23-f9b8-4e21-a714-800a9fbb448e" />

</p>
<ol>
<li>대상 그룹에서는 EC2 인스턴스를 등록하고, 해당 EC2 인스턴스의 상태 확인을 할 수 있으며, 상태 확인을 위해 대상 그룹에 포트를 설정할 수 있다.
<ul>
<li>아파치가 설치된 EC2 인스턴스 가정
<ul>
<li>
<p>아파치는 기본적으로 80번 포트를 사용하므로 대상 그룹에서는 동일한 포트 설정</p>
<p>→ 대상 그룹은 EC2 인스턴스의 웹 서버 동작을 확인할 수 있다.</p>
</li>
<li>
<p>EC2 인스턴스가 80번 포트를 통해 문제없이 서버로써의 기능을 하면 대상 그룹은 healthy 반환</p>
</li>
<li>
<p>80번 포트를 통해 웹 서버가 동작하지 않으면 unhealthy 반환</p>
</li>
</ul>
</li>
</ul>
</li>
</ol>
<ul>
<li>
<p>로드 밸런서에서는 HTTPS 즉 443 포트 사용 지원</p>
<ul>
<li>ALB에서는 443 포트를 사용하는 HTTPS 프로토콜 지정 가능</li>
<li>NLB에서는 443 포트를 사용하는 TLS 프로토콜 지정 가능</li>
</ul>
</li>
<li>
<p>이런 프로토콜을 사용하려면 사용자 컴퓨터와 서버 사이의 암호화된 연결을 수립해야 한다.</p>
<p>→ SSL/TLS 인증서를 발급받아 설정 필요</p>
<ul>
<li>AWS ACM을 사용해 인증서 발급, 외부 업체를 통해 인증서를 발급받아 불러올 수도 있음</li>
</ul>
</li>
</ul>
<h3>HTTPS/TLS 프로토콜 지정 시 로드 밸런서의 동작 방식</h3>
<p>

<img width="584" height="371" alt="Image" src="https://github.com/user-attachments/assets/231600c4-47b3-4b98-adcc-ea1cfd98177f" />

</p>
<ol>
<li>사용자는 브라우저에서 HTTPS 프로토콜을 이용해 웹사이트에 접근할 수 있다.
<ul>
<li>AWS ACM 또는 외부 인증서를 로드 밸런서에 등록했기 때문</li>
</ul>
</li>
<li>로드 밸런서 노드를 이용해 부하 분산할 가용 영역을 구분짓는다.</li>
<li>대상 그룹에서는 부하 분산을 시도할 EC2 인스턴스를 관리하며 상태를 확인한다.</li>
</ol>
<p>⇒ 사용자는 로드 밸런서를 포함해 클라우드 내부에서의 작동에 대해 걱정할 필요 없이 안전하게 웹사이트에 접근할 수 있다.</p>
<h3>리스너</h3>
<p>n개의 대상 그룹을 생성했고, 이 대상 그룹은 각각 웹 서비스를 제공하는 EC2 인스턴스와 API를 처리하는 EC2 인스턴스로 구분한다.</p>
<p>이때 도메인으로 로드 밸런서에 접근한다면 어느 EC2 인스턴스에 접근하게 될까?</p>
<p>⇒ 리스너를 통해 n개의 대상 그룹을 운영할 때 어떤 방식으로 접근할 지 설정한다.</p>
<ul>
<li>리스너 규칙 설정
<ul>
<li>포트 기반 라우팅 : 프로토콜, 포트 지정, 대상 그룹 연결</li>
<li>경로 기반 라우팅
<ul>
<li>/web 경로로 접근 → EC2 A의 /web 경로에 설정되어 있는 페이지/파일이 열림</li>
<li>/api 경로로 접근 → EC2 B의 /api 경로에 설정되어 있는 페이지/파일이 열림</li>
</ul>
</li>
<li>포트 기반 라우팅 + 경로 기반 라우팅
<ul>
<li>특정 경로에 대한 접근 권한을 제어해 보안 강화</li>
<li>ex) /admin 경로는 관리자 전용 기능에만 접근할 수 있도록 설정</li>
</ul>
</li>
</ul>
</li>
</ul>
<h3>고정 응답 반환 규칙</h3>
<ul>
<li>특정 경로에 접근하고자 하는 사용자에게 응답 코드와 텍스트를 반환하는 규칙</li>
<li>잘못된 URL로 접근했을 경우나 웹 서버가 점검 중이면 주로 사용된다.
<ul>
<li>잘못된 도메인으로 접근한 경우 에러 코드와 텍스트 반환</li>
</ul>
</li>
</ul>
<h2>3.3 부하 분산을 위한 로드 밸런서의 알고리즘</h2>
<p><strong>라운드 로빈</strong></p>
<ul>
<li>클라이언트로부터 받은 요청을 로드밸런싱 대상 서버에 순서대로 할당받음</li>
<li>부하 분산할 대상 서버의 성능이 동일, 처리 시간이 짧은 애플리케이션에서 사용</li>
</ul>
<p><strong>가중치 랜덤</strong></p>
<ul>
<li>정상 작동하는 서버에 임의의 순서로 요청 라우팅</li>
<li>가중치 랜덤 알고리즘은 <strong>ATW(Automatic Target Weights</strong>)를 대응
<ul>
<li>ATW: ALB 뒤에 있는 대상 서버의 장애, 성능 저하를 감지해 다른 서버로 자동으로 트래픽을 전달하는 기능</li>
<li>가중치 랜덤 알고리즘과 함께 사용되어, 비정상적인 대상을 식별하고 트래픽을 삭제하고 오류가 발생하지 않은 대상에 자동으로 트래픽 전달</li>
</ul>
</li>
</ul>
<p><strong>최소 미해결 요청</strong></p>
<ul>
<li>연결 수가 가장 적은 서버로 라우팅</li>
<li>동적인 분산 알고리즘 → 각 서버에 대한 현재 연결 수를 동적으로 카운트, 동적으로 변하는 요청에 대한 부하 분산</li>
</ul>
<p>이런 로드 밸런서 알고리즘은 ALB에서 사용되며, NLB에서는 AWS 하이퍼플래인이라는 AWS의 부하 분산 기술을 사용한다.</p>
<p>ALB와 NLB에서 교차 영역 로드 밸런싱을 이용할 수 있다.</p>
<ul>
<li>ALB는 항상 교차 영역 로드 밸런싱이 유효화되어 있는 상태로 무효화시킬 수 없다.</li>
<li>NLB는 교차 영역 로드 밸런싱을 유효화할지 무효화할지 선택할 수 있다.
<ul>
<li>무효화한 상태라면 가용 영역에 따라 균등하게 부하 분산을 수행하지 않는다.</li>
<li>유효화하면 균등하게 각 가용 영역으로 부하 분산을 수행한다.</li>
<li>기본적으로는 무효화로 설정되어 있다.</li>
</ul>
</li>
</ul>

# 2. 부하 분산 서비스, 탄력적 로드 밸런서란?

탄력적 로드 밸런서를 사용하면 사용자가 급증하더라도 적절하게 트래픽을 부하 분산할 수 있어 안정적으로 서버를 운영할 수 있다.

- 탄력적 로드 밸런서는 웹 서버 앞에 배치되며, 사용자는 이 탄력적 로드 밸런서를 경유해 웹 사이트로 접근한다.
- 외부로 웹 서버를 공개할 필요가 없어지며, 사용자는 탄력적 로드 밸런서를 통해서만 웹 사이트를 접근할 수 있다.

 ⇒ 서버의 보안을 강화하고, 사용자에게 안정적인 서비스 제공

## 탄력적 로드 밸런서를 경유해 웹 서버에 접속하는 방법

- 탄력적 로드 밸런서는 퍼블릿 서브넷에 배치
- 탄력적 로드 밸런서에서는 이 서비스에 접근할 수 있는 DNS 이름을 별도로 제공
- 아마존 라우트53과 연동해 별도로 도메인 할당 가능
- EC2 인스턴스에 도메인 할당하는 것이 아닌 탄력적 로드 밸런서에 도메인을 할당
    - ex) [goldenrabbit.co.kr](http://goldenrabbit.co.kr/)

⇒ 사용자는 탄력적 로드 밸런서의 도메인을 사용해 웹사이트에 접근하면서도 사용자와 EC2 인스턴스 간 직접적인 접근을 완전히 차단할 수 있다.

- 탄력적 로드 밸런서에서는 프라이빗 서브넷에 있는 EC2 인스턴스로 부하 분산을 시도
- 여러 가용 영역에 걸쳐 부하 분산 실시

⇒ 하나의 가용 영역에 무너지더라도 다른 가용 영역에서 서비스를 지속할 수 있다.

## 탄력적 로드 밸런서와 연동 가능한 서비스

- 아마존 EC2 오토스케일 → 서버 확장
- 아바존 ECS → 컨테이너 서비스
- 아마존 라우트53 →  도메인 라우팅
- 아마존 클라우드프론트 → 고속 콘텐츠 전송 지원
- 아마존 S3 서비스 → 접속 로그 기록 등

## 3.1 로드 밸런서의 작동 방식

로드 밸런서에서는 로드 밸런서를 퍼블릭 서브넷에 생성할지, 프라이빗 서브넷에 생성할지 선택할 수 있다.

### 퍼블릭 서브넷 VS 프라이빗 서브넷에 생성

1. 퍼블릭 서브넷에 로드 밸런서를 생성
    - 외부 사용자에게 웹사이트를 공개해 웹 서비스를 제공하고 싶을 때
2. 프라이빗 서브넷에 로드 밸런서를 생성
    - 사내에서만 특정 웹 서비스를 제공하고 싶을 때

로드 밸런서를 생성할 때 외부로 공개할지, 내부에서만 사용할지 설계 단계에서 반드시 고민해야 한다.

### 로드 밸런서가 가용 영역을 구분하고 부하 분산을 실시하는 방법

각 가용 영역에 로드 밸런서의 부하 분산을 도와주는 **로드 밸런서 노드**가 생성되기 때문이다.

로드 밸런서를 생성하면 선택한 서브넷에 로드 밸런서 노드가 생성되며, 이 로드 밸런서 노드로 인해 각 가용 영역을 구분지을 수 있고 부하 분산을 수행할 수 있다.

### 보안 그룹 설정

로드 밸런서는 EC2 인스턴스와 동일하게 보안 그룹을 설정할 수 있으며, 로드 밸런서로 접근하고자 하는 사용자를 제한할 수 있다.

- 외부에 공개되는 웹사이트는 보안 그룹을 완전히 오픈
    - 이후 EC2 인스턴스의 보안 그룹을 수정해 로드 밸런서의 접근만을 허용하면, 외부에서 접근하는 사용자는 로드 밸런서에만 접근할 수 있고, 직접적으로는 EC2 인스턴스에 접근할 수 없다.
- 특정 사용자 그룹만 로드 밸런서에 접근하도록 제한하고자 하는 경우 보안 그룹 수정
    - EC2 인스턴스에는 개발자, 관리자 등 특정 그룹만 접근하도록 보안 그룹을 설정해 보안성 높임

## 3.2 로드 밸런서의 대상 그룹과 리스너

### 대상 그룹

로드 밸런서 노드는 가용 영역을 구분하는 용도로 생성되는 것이며, 부하 분산을 할 EC2 인스턴스를 선택할 수 없다.

- 대상 그룹은 로드 밸런서 노드와 EC2 인스턴스 사이의 중간 다리 역할
- 부하 분산을 시도할 EC2 인스턴스를 등록하고 관리
- 로드 밸런서는 로드 밸런서 노드를 통해 가용 영역을 구분하고, 대상 그룹을 통해 부하 분산을 수행하고자 하는 EC2 인스턴스를 구분할 수 있다.
    - 대상 그룹은 n개로 나눠 생성
    - EC2 인스턴스의 역할에 따라 대상 그룹을 구분하는 것이 바람직
        - ex) 하나의 대상 그룹에는 웹 서비스를 제공하는 EC2 인스턴스를 등록, 또 하나의 대상 그룹에는 API를 처리하는 EC2 인스턴스 등록

![image.png](attachment:a5ff8395-17f7-4d7b-b5ea-5d4ed9894670:image.png)

1. 대상 그룹에서는 EC2 인스턴스를 등록하고, 해당 EC2 인스턴스의 상태 확인을 할 수 있으며, 상태 확인을 위해 대상 그룹에 포트를 설정할 수 있다.
    - 아파치가 설치된 EC2 인스턴스 가정
        - 아파치는 기본적으로 80번 포트를 사용하므로 대상 그룹에서는 동일한 포트 설정
            
            → 대상 그룹은 EC2 인스턴스의 웹 서버 동작을 확인할 수 있다.
            
        - EC2 인스턴스가 80번 포트를 통해 문제없이 서버로써의 기능을 하면 대상 그룹은 healthy 반환
        - 80번 포트를 통해 웹 서버가 동작하지 않으면 unhealthy 반환
- 로드 밸런서에서는 HTTPS 즉 443 포트 사용 지원
    - ALB에서는 443 포트를 사용하는 HTTPS 프로토콜 지정 가능
    - NLB에서는 443 포트를 사용하는 TLS 프로토콜 지정 가능
- 이런 프로토콜을 사용하려면 사용자 컴퓨터와 서버 사이의 암호화된 연결을 수립해야 한다.
    
    → SSL/TLS 인증서를 발급받아 설정 필요
    
    - AWS ACM을 사용해 인증서 발급, 외부 업체를 통해 인증서를 발급받아 불러올 수도 있음

### HTTPS/TLS 프로토콜 지정 시 로드 밸런서의 동작 방식

![image.png](attachment:55c1d040-31c4-4fab-be94-8b487edb13bb:image.png)

1. 사용자는 브라우저에서 HTTPS 프로토콜을 이용해 웹사이트에 접근할 수 있다.
    - AWS ACM 또는 외부 인증서를 로드 밸런서에 등록했기 때문
2. 로드 밸런서 노드를 이용해 부하 분산할 가용 영역을 구분짓는다.
3. 대상 그룹에서는 부하 분산을 시도할 EC2 인스턴스를 관리하며 상태를 확인한다.

⇒ 사용자는 로드 밸런서를 포함해 클라우드 내부에서의 작동에 대해 걱정할 필요 없이 안전하게 웹사이트에 접근할 수 있다.

### 리스너

n개의 대상 그룹을 생성했고, 이 대상 그룹은 각각 웹 서비스를 제공하는 EC2 인스턴스와 API를 처리하는 EC2 인스턴스로 구분한다.

이때 도메인으로 로드 밸런서에 접근한다면 어느 EC2 인스턴스에 접근하게 될까?

⇒ 리스너를 통해 n개의 대상 그룹을 운영할 때 어떤 방식으로 접근할 지 설정한다.

- 리스너 규칙 설정
    - 포트 기반 라우팅 : 프로토콜, 포트 지정, 대상 그룹 연결
    - 경로 기반 라우팅
        - /web 경로로 접근 → EC2 A의 /web 경로에 설정되어 있는 페이지/파일이 열림
        - /api 경로로 접근 → EC2 B의 /api 경로에 설정되어 있는 페이지/파일이 열림
    - 포트 기반 라우팅 + 경로 기반 라우팅
        - 특정 경로에 대한 접근 권한을 제어해 보안 강화
        - ex) /admin 경로는 관리자 전용 기능에만 접근할 수 있도록 설정

### 고정 응답 반환 규칙

- 특정 경로에 접근하고자 하는 사용자에게 응답 코드와 텍스트를 반환하는 규칙
- 잘못된 URL로 접근했을 경우나 웹 서버가 점검 중이면 주로 사용된다.
    - 잘못된 도메인으로 접근한 경우 에러 코드와 텍스트 반환

## 3.3 부하 분산을 위한 로드 밸런서의 알고리즘

**라운드 로빈**

- 클라이언트로부터 받은 요청을 로드밸런싱 대상 서버에 순서대로 할당받음
- 부하 분산할 대상 서버의 성능이 동일, 처리 시간이 짧은 애플리케이션에서 사용

**가중치 랜덤**

- 정상 작동하는 서버에 임의의 순서로 요청 라우팅
- 가중치 랜덤 알고리즘은 **ATW(Automatic Target Weights**)를 대응
    - ATW: ALB 뒤에 있는 대상 서버의 장애, 성능 저하를 감지해 다른 서버로 자동으로 트래픽을 전달하는 기능
    - 가중치 랜덤 알고리즘과 함께 사용되어, 비정상적인 대상을 식별하고 트래픽을 삭제하고 오류가 발생하지 않은 대상에 자동으로 트래픽 전달

**최소 미해결 요청**

- 연결 수가 가장 적은 서버로 라우팅
- 동적인 분산 알고리즘 → 각 서버에 대한 현재 연결 수를 동적으로 카운트, 동적으로 변하는 요청에 대한 부하 분산

이런 로드 밸런서 알고리즘은 ALB에서 사용되며, NLB에서는 AWS 하이퍼플래인이라는 AWS의 부하 분산 기술을 사용한다. 

ALB와 NLB에서 교차 영역 로드 밸런싱을 이용할 수 있다.

- ALB는 항상 교차 영역 로드 밸런싱이 유효화되어 있는 상태로 무효화시킬 수 없다.
- NLB는 교차 영역 로드 밸런싱을 유효화할지 무효화할지 선택할 수 있다.
    - 무효화한 상태라면 가용 영역에 따라 균등하게 부하 분산을 수행하지 않는다.
    - 유효화하면 균등하게 각 가용 영역으로 부하 분산을 수행한다.
    - 기본적으로는 무효화로 설정되어 있다.

## 3.4 환경별 로드 밸런서 구성 패턴 살펴보기

1. 환경별로 로드 밸런서 나누기
    - 실전 환경, 개발 환경으로 나눠 접속
    - 장점
        - 각 환경에 발생하는 문제 분산
            - 개발 환경에서 발생한 문제를 실전 환경에 영향 없도록 함
        - 트래픽과 리소스 사용률을 분리 및 관리
        - 각 환경에 맞는 액세스 제어 정책 적용 가능
            - 실전 환경, 개발 환경을 나누어 보안 등급을 나눠 설정
        - 각 환경별로 로드 밸런서를 독립적으로 확장, 성능 조절 가능
    - 가장 일반적이며 이상적
2. 하나의 로드 밸런서로 실전 환경, 개발 환경 제어
    - 로드 밸런서에 장애 발생 시 두 환경 모두에 영향
    - 하나의 로드 밸런서로 두 환경에 접근하려면 리스너 규칙 추가
        - 포트 기반 라우팅: 실전 환경은 443, 개발 환경은 444 포트와 같이 리스너 규칙을 추가해 접근
        - 경로 기반 라우팅: [~.co.kr/dev/와](http://~.co.kr/dev/%EC%99%80) 같은 경로로 접근할 수 있도록 리스너 규칙 추가
    - 리스너 규칙 복잡, 관리 어려움

    ```yaml
    AWSTemplateFormatVersion: "2010-09-09"
    Description:
      Create ALB or S3 Bucket
    
    # ------------------------------------------------------------#
    # Input Parameters
    # ------------------------------------------------------------# 
    Parameters:
      SystemName:
        Description: "System name of each resource names."
        Type: String
        Default: "gr"
      EnvName:
        Description: "Environment name of each resource names."
        Type: String
        Default: "product"
    
    # ------------------------------------------------------------#
    #  Target Group
    # ------------------------------------------------------------#
    Resources:
      ALBTargetGroup: 
        Type: AWS::ElasticLoadBalancingV2::TargetGroup
        Properties: 
          # 다른 스택(VPC 스택 등)에서 Export한 VPC ID를 동적으로 가져옴
          VpcId: 
            Fn::ImportValue: !Sub ${EnvName}-vpc
          Name: !Sub ${SystemName}-${EnvName}-tgp
          Protocol: HTTP
          Port: 80
          
          # 헬스 체크 설정: 인스턴스의 '생존'뿐만 아니라 '정상 응답' 여부를 판단하는 기준
          HealthCheckProtocol: HTTP
          HealthCheckPath: "/"
          HealthCheckPort: "traffic-port"
          HealthyThresholdCount: 5    # 이 횟수만큼 연속 성공해야 '정상'으로 간주
          UnhealthyThresholdCount: 2  # 이 횟수만큼 연속 실패하면 '장애'로 간주하여 트래픽 차단
          HealthCheckTimeoutSeconds: 5 
          HealthCheckIntervalSeconds: 60 
          Matcher: 
            HttpCode: 200 # 성공으로 간주할 HTTP 상태 코드
          
          Tags:
            - Key: Name
              Value: !Sub ${SystemName}-${EnvName}-tgp
            - Key: Env
              Value: !Sub ${EnvName}
          
          # 타겟 그룹에 연결할 실제 리소스 (여기서는 EC2)
          Targets: 
            - Id: 
                Fn::ImportValue: !Sub ${EnvName}-ec2
              Port: 80
    
    # ------------------------------------------------------------#
    #  internet-facing ALB
    # ------------------------------------------------------------#
      InternetFacingALB: 
        Type: AWS::ElasticLoadBalancingV2::LoadBalancer
        Properties: 
          Name: !Sub ${SystemName}-${EnvName}-alb
          # Scheme: 외부(Public) 접속을 허용하려면 internet-facing, 내부용은 internal
          Scheme: "internet-facing"
          
          LoadBalancerAttributes: 
            # 실수로 ALB가 삭제되는 것을 방지 (운영 환경에서는 true 권장)
            - Key: "deletion_protection.enabled"
              Value: false
            # 연결 유지 시간: 백엔드 API 처리 시간을 고려하여 설정
            - Key: "idle_timeout.timeout_seconds"
              Value: 60
          
          # ALB에 적용할 보안 그룹 (80/443 포트가 열려있어야 함)
          SecurityGroups:
            - Fn::ImportValue: !Sub ${EnvName}-alb-sg
          
          # 고가용성(HA)을 위해 반드시 2개 이상의 가용 영역(AZ) 서브넷을 지정해야 함
          Subnets: 
            - Fn::ImportValue: !Sub ${EnvName}-public-subnet-1a
            - Fn::ImportValue: !Sub ${EnvName}-public-subnet-1b
          Type: application
    
    # ------------------------------------------------------------#
    #  Set ALB Listner
    # ------------------------------------------------------------#
      ALBListenerHTTP:
        Type: AWS::ElasticLoadBalancingV2::Listener
        Properties:
          # ALB가 리스닝할 포트
          Port: 80
          Protocol: HTTP
          # 리스너가 받은 요청을 어떤 타겟 그룹으로 보낼지 정의 (Forward)
          DefaultActions:
            - TargetGroupArn: !Ref ALBTargetGroup
              Type: forward
          LoadBalancerArn: !Ref InternetFacingALB
    
    # ------------------------------------------------------------
    # Output Parameters
    # ------------------------------------------------------------
    Outputs:
      InternetFacingALB:
        Description: "The ARN of the ALB"
        Value: !Ref InternetFacingALB
        # 다른 CloudFormation 스택에서 이 ALB를 참조할 수 있도록 Export
        Export:
          Name: !Sub ${EnvName}-alb
    ```
