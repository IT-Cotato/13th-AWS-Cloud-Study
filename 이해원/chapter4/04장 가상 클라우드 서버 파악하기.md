<h2>2.3 스토리지 옵션</h2>
<p>EC2에서는 두 가지 스토리지 옵션을 선택할 수 있다.</p>
<ul>
<li>인스턴스 스토어 볼륨</li>
<li>EBS 볼륨</li>
</ul>
<h3>인스턴스 스토어 볼륨</h3>
<ul>
<li>
<p>휘발성 스토리지</p>
</li>
<li>
<p>EC2 인스턴스의 내장 디스크</p>
</li>
<li>
<p>장점</p>
<ul>
<li>EBS 볼륨보다 높은 IOPS 및 처리량
<ul>
<li>IOPS : 스토리지의 성능 지표, 1초간 읽고 쓸 수 있는 횟수</li>
</ul>
</li>
<li>낮은 대기 시간</li>
</ul>
<p>⇒ 높은 I/O 성능이 필요한 스토리지에 이상적</p>
</li>
<li>
<p>단점</p>
<ul>
<li>휘발성이므로 임시 스토리지도 활용</li>
<li>디스크 장애 발생 or EC2 인스턴스가 중지/삭제된 경우 데이터 손실
<ul>
<li>EC2 인스턴스 재부팅의 경우 데이터 손실 발생 X</li>
</ul>
</li>
<li>백업 불가능 → 손실된 데이터 복구 불가</li>
<li>EC2 인스턴스에서 분리하는 것 불가능</li>
</ul>
</li>
</ul>
<p>
<img width="1119" height="259" alt="Image" src="https://github.com/user-attachments/assets/71b4d52b-b37a-4bba-b898-b7c72cd56fcc" />
</p>
<p>인스턴스 유형 선택 시, 인스턴스 스토어 볼륨의 사용 유무를 확인할 수 있으며, 스토리지 용량과 유형을 확인할 수 있다.</p>
<h3>EBS 볼륨</h3>
<p><a href=""></a></p>
<ul>
<li>
<p>EC2 인스턴스와 별개로 독립적으로 관리되는 서비스</p>
</li>
<li>
<p>EC2 인스턴스 없이 유지되므로 별도 비용 발생</p>
</li>
<li>
<p>장점</p>
<ul>
<li>복수의 EBS 볼륨을 생성해 EC2 인스턴스에 연결 가능</li>
<li>백업 및 복원 → 데이터 손실 방지</li>
<li>비휘발성 → EC2 인스턴스를 중지/삭제해도 데이터 손실 X</li>
</ul>
<p>⇒ 특수한 상황이 아니라면 EBS 볼륨 사용이 권장된다.</p>
</li>
</ul>
<blockquote>
<p>독립적으로 관리되는 EBS 볼륨이라 할지라도 EC2 인스턴스가 삭제될 때 연결된 볼륨을 자동으로 삭제할 수 있는 옵션을 선택할 수 있다.</p>
<p>AWS 관리 콘솔에서 EC2 인스턴스를 생성했다면 루트 볼륨은 EC2 인스턴스 삭제 시 자동으로 삭제된다.</p>
<p>필요에 따라 해당 EC2 인스턴스만 삭제하고 연결된 EBS 볼륨을 유지할 수 있다.</p>
</blockquote>
<h3>EBS 볼륨 유형</h3>
<ul>
<li>SSD 볼륨</li>
<li>HDD 볼륨</li>
</ul>

| 볼륨 범주 | 볼륨 유형 | 주요 특징 | 비고 (사용 사례) |
|---|---|---|---|
| SSD 지원 | 범용 SSD<br>(gp3 / gp2) | • 성능과 비용의 균형이 가장 좋음<br>• gp3: 저장 용량과 무관하게 IOPS와 처리량을 독립적으로 설정 가능 | 가상 데스크톱, 중소규모 DB, 웹 서버, 개발/테스트 환경<br>(대부분의 작업에 권장) |
| SSD 지원 | 프로비저닝된 IOPS<br>(io2 / io1) | • 최고 성능. 지연시간에 극도로 민감한 작업용<br>• io2: 99.999%의 높은 내구성 제공 및 가장 높은 IOPS 지원 | SAP HANA, Oracle 등 대규모 고성능 데이터베이스, 비즈니스 크리티컬 애플리케이션 |
| HDD 지원 | 처리량 최적화<br>(st1) | • 대용량 처리 중심. 초당 처리량(MB/s)이 중요하고 데이터 액세스가 빈번한 작업에 적합 | 빅데이터, 데이터 웨어하우스, 로그 처리, ETL 작업<br>(시스템 부팅용으로 사용 불가) |
| HDD 지원 | Cold HDD<br>(sc1) | • 최저 비용. 데이터 액세스 빈도가 매우 낮은 아카이브용으로 최적화 | 백업 데이터, 아카이브, 접근 빈도가 낮은 데이터 보관용 스토리지 |


- 일반적으로 널리 사용되는 유형은 범용 SSD(gp2 및 gp3)
    - 어떤 볼륨 유형 선택할 지 망설여진다면 범용 SSD 선택 권장
    - gp3
        - GB당 최대 20% 비용 절감 제공
        - 저렴한 비용으로 더 적은 볼륨을 프로비저닝할 수 있어 더 높은 성능 유지
        
        ⇒ 볼륨 유형은 SSD gp3의 사용을 권장한다.
        

> 프로비저닝(Provisioning)
> 
> - 하드웨어, 네트워크, 가상 머신 및 기타 리소스를 포함하는 IT 인프라를 설정하고 시스템과 사용자가 리소스와 데이터를 사용할 수 있도록 하는 프로세스
> - 사용자가 클라우드 자원(용량, IOPS, 처리량 등)의 스펙을 결정하여 할당받는 행위

| OS | 드라이버 타입 | 가상화 | 사용 가능 | 루트용으로 예약됨 | EBS 볼륨으로 권장 |

| 리눅스 | - | HVM | /dev/sd[az]<br>/dev/sd[az][1-15]<br>/dev/hd[az]<br>/dev/hd[az][1-15] | /dev/sda1 | /dev/sd[fp]<br>/dev/sd[fp][1-6] |

<ul>
<li>
<p>윈도우</p>
<ul>
<li>사용 가능한 디바이스 이름을 알기 위해 내가 사용하는/사용할 드라이버 타입 확인</li>
<li>EC2에서 AWS가 제공하는 윈도우 서버는 초기 상태에서 반가상화 드라이버 등의 특수 드라이버가 설치되어 있음
<ul>
<li>윈도우(HVM 방식)가 반가상화(PV)처럼 하이퍼바이저와 통신하도록 도움</li>
<li>AWS PV 드라이버</li>
<li>C 드라이브 즉 루트 볼륨으로 /dev/sda1 디바이스 이름 사용할 수 있도록 예약</li>
</ul>
</li>
</ul>
</li>
<li>
<p>리눅스</p>
<ul>
<li>가상화로 디바이스 이름이 나눠짐</li>
<li>가상화 : 물리적인 서버 한 대를 여러 대의 가상 서버로 나누는 기술</li>
<li><strong>전가상화 HVM</strong> : 하드웨어 전체를 가상화
<ul>
<li>OS를 수정할 필요 없음 → 설치, 구성 용이</li>
<li>하드웨어 자체가 완전가상화를 지원해야 하므로 퍼포먼스가 떨어짐</li>
</ul>
</li>
<li><strong>반가상화PV</strong>  : 하드웨어 일부를 가상화
<ul>
<li>하이퍼바이저(관리자)를 통해 하드웨어 제어 → 좋은 퍼포먼스</li>
</ul>
</li>
</ul>
<blockquote>
<p>AWS에서는 현재 전가상화를 적극 지원하고 있으며, 최고의 퍼포먼스를 위해 인스턴스를 시작할 때 최신 세대의 인스턴스 유형과 전가상화 사용을 권장한다.</p>
</blockquote>
</li>
</ul>
<h2>2.4 보안 그룹</h2>
<ul>
<li>네트워크 트래픽을 관리하는 서비스</li>
<li>특정 IP 주소, IP 범위, 포트 및 프로토콜을 기반으로 특정 리소스에 대한 접근을 허용/거부</li>
</ul>
<p>

<img width="1112" height="565" alt="Image" src="https://github.com/user-attachments/assets/49329067-6ccd-4387-9b5d-be46f87ddfbc" />

</p>
<ul>
<li>보안 그룹에서 22번 포트 접속에 대해 A 사용자의 IP 주소만 허용했다면, B 사용자는 이 포트를 통한 접속이 차단된다. → 보안 그룹을 통한 EC2 인스턴스로의 접근을 제어할 수 있다.</li>
</ul>
<h3>보안 그룹의 인바운드/아웃바운드 규칙</h3>
<p>

<img width="934" height="302" alt="Image" src="https://github.com/user-attachments/assets/0998d33e-ea8a-44df-8b5f-d93d81d7897b" />

</p>
<p>EC2 인스턴스에 대한 액세스(인바운드 트래픽), 인스턴스에서의 액세스(아웃바운드 트래픽)에 대해 방화벽 역할을 하는 것이 보안 그룹이다.</p>
<p>일반적으로 보안 그룹을 구성할 때는 인바운드 규칙에 집중한다.</p>
<ul>
<li>인바운드 규칙 : 외부에서 EC2 인스턴스로의 접근을 어떻게 허용/제한할지 결정</li>
<li>아웃바운드 트래픽 : 기본적으로 EC2 인스턴스에서 외부로 모든 트래픽을 내보낼 수 있도록 설정
<ul>
<li>보안 그룹 설정에서 특별한 제한이 없다면 EC2 인스턴스는 외부로의 통신에 필요한 모든 네트워크 연결을 수행할 수 있도록 설정</li>
</ul>
</li>
</ul>
<h3>EC2 네트워크: IP 주소와 접근성</h3>
<ul>
<li>EC2 인스턴스는 IP 주소를 가짐</li>
<li>네트워크 연결 : EC2 ↔ 온프레미스 간 상호 접근 허용</li>
<li>EC2 인스턴스는 퍼블릭 IP, 프라이빗 IP 주소가 할당됨 (퍼블릭 서브넷)
<ul>
<li>
<p>퍼블릭 IP (공인 IP) : 인터넷을 통한 외부 접근용</p>
<ul>
<li>EC2 인스턴스 재부팅/재시작할 때마다 변경 → 동적 IP 할당 방식</li>
</ul>
<p>⇒ <strong>탄력적 IP 주소</strong>로 IP를 고정시킬 수 있다.</p>
</li>
<li>
<p>프라이빗 IP (사설 IP) : AWS 내부망 및 온프레미스 연동용</p>
<ul>
<li>프라이빗 서브넷에 생성된 EC2 인스턴스는 프라이빗 IP 주소만 할당</li>
</ul>
</li>
</ul>
</li>
</ul>
<h2>2.5 키 페어</h2>
<ul>
<li>EC2 인스턴스에 안전하게 접속하는 필수 요소</li>
<li>키 페어가 없으면 EC2 인스턴스 로그인/접속 불가</li>
<li>키 페어 유형
<ul>
<li>RSA : 범용 키 페어 형식, 모든 OS에서 이용 가능</li>
<li>ED25519 : 2021년 공개된 유형, 리눅스와 맥 OS에서만 사용 가능
<ul>
<li>RSA보다 키 길이가 짧고 고속 처리 → 좋은 퍼포먼스</li>
</ul>
</li>
</ul>
</li>
</ul>
<blockquote>
<p>우분투 20.04까지는 RSA를 사용할 수 있지만 우분투 22.04에서는 ED25519를 사용해야 한다.</p>
<p>기본적으로 RSA를 많이 사용하지만, 특정 환경이나 요구사하엥 따라서는 새로운 버전에서 ED25519를 사용하는 것이 적합할 수 있다.</p>
</blockquote>
<ul>
<li>키 파일 형식
<ul>
<li>.pem(Privacy Enhanced Mail) : OpenSSH를 사용하는 환경에서 사용</li>
<li>.ppk(PuTTY Private Key) : PuTTY에서 사용</li>
</ul>
</li>
</ul>

						VolumeSize: 100 # 볼륨 크기 (100GB)

<h1>4. 아마존 EC2 접속 패턴 살펴보기</h1>
<p>EC2 인스턴스를 퍼블릭 환경에 배치하고 인터넷에 노출시키면 보안 문제가 발생할 수 있다.</p>
<p>EC2 인스턴스를 프라이빗 서브넷에 배치하여 폐쇄망을 통해 접속하는 등 다양한 배치 방법에 따라 접속 방법이 달라지게 되는데, EC2 인스턴스 배치에 따른 다양한 접속 패턴을 알아보자.</p>
<h2>4.1 인터넷을 통한 EC2 인스턴스 접속</h2>
<ul>
<li>
<p>EC2 인스턴스&gt;연결에서 퍼블릭 IP를 사용하여 연결을 클릭해 접속</p>
<p>

<img width="1000" height="724" alt="Image" src="https://github.com/user-attachments/assets/28699138-d294-42fe-b484-8986f9a55a37" />

</p>
</li>
<li>
<p>AWS 관리 콘솔에서 키 페어 없이 EC2 인스턴스에 접속 가능</p>
</li>
<li>
<p>EC2 인스턴스에 퍼블릭 IP 주소가 할당되어 있어야 하고, 반드시 퍼블릭 서브넷에 배치되어 있어야 함</p>
</li>
<li>
<p>가장 심플하지만 EC2 인스턴스를 인터넷에 노출시키고 있기 때문에 권장하지 않음</p>
</li>
</ul>
<blockquote>
<p>[퍼블릭 IP를 사용하여 연결] 기능은 과거에는 [E]라는 이름으로 불렸으며, 현업에서는 여전히 이 명칭으로 자주 사용되라</p>
</blockquote>
<h2>4.2 EC2 인스턴스 연결 엔드포인트 이용</h2>
<h3>EIC(EC2 Instance Connect Endpoint)를 활용한 접속 방법</h3>
<ul>
<li>인터넷 게이트웨이, NAT 게이트웨이 없이 EC2 인스턴스로 접속할 수 있는 서비스</li>
</ul>
<p>

<img width="1027" height="577" alt="Image" src="https://github.com/user-attachments/assets/34051b0e-1ab7-458d-b72c-a9271f64f84d" />

</p>
<p>&lt;생성할 구성&gt;</p>
<p>

<img width="1031" height="706" alt="Image" src="https://github.com/user-attachments/assets/bc33dd27-44f4-4383-8209-e6fb46808c70" />

</p>
<ul>
<li>
<p>EIC를 이용한다면 인터넷 게이트웨이와 NAT 게이트웨이 생성은 불필요</p>
<ul>
<li>외부와의 통신이 완전히 차단된 상황이므로 yum 패키지 사용 등이 필요하다면 NAT 게이트웨이를 생성해야 한다.</li>
</ul>
<p>→ NAT 게이트웨이를 함께 배치하거나, 더 이상 yum 패키지 사용이 불필요하다면 생성한 NAT 게이트웨이를 제거해 비용 문제를 해결하거나 외부와의 통신을 차단할 수 있다.</p>
</li>
</ul>
<ol>
<li>
<p>EC2에서 퍼블릭 IP 할당 불필요</p>
<pre><code class="language-yaml">      SecurityGroupIds: # 서브넷과 보안 그룹을 개별적으로 설정
        - Fn::ImportValue: !Sub ${EnvName}-ec2-sg
      SubnetId: 
        Fn::ImportValue: !Sub ${EnvName}-web-subnet-1a # 프라이빗 서브넷으로 변경
</code></pre>
</li>
<li>
<p>VPC.yml에 EC2 인스턴스 연결 엔드포인트에서 사용할 보안 그룹 생성</p>
<pre><code class="language-yaml">  EicSg:
    Type: AWS::EC2::SecurityGroup 
    Properties:
      GroupName: !Sub ${SystemName}-${EnvName}-sg-eic
      GroupDescription: !Sub ${SystemName}-${EnvName}-sg-eic
      VpcId: !Ref VPC
      
      # 아웃바운드 규칙
      SecurityGroupEgress:
        - IpProtocol: -1 # '-1'은 모든 프로토콜(TCP, UDP, ICMP 등)을 의미
          CidrIp: 0.0.0.0/0 #모든 트래픽 허용
</code></pre>
</li>
<li>
<p>EC2 인스턴스 연결 엔드포인트 생성</p>
<pre><code class="language-yaml">	Eic:
    Type: AWS::EC2::InstanceConnectEndpoint # EC2 인스턴스 연결 엔드포인트 생성
    Properties:
      SecurityGroupIds:
        - !Ref EicSg 
      SubnetId: !Ref WebSubnet1a # 프라이빗 서브넷에 EIC 생성
</code></pre>
</li>
<li>
<p>EC2 인스턴스 연결 엔드포인트의 접속을 허용하도록 EC2 인스턴스 보안 그룹 수정</p>
<pre><code class="language-yaml">      SecurityGroupIngress: # 허용할 IP 주소 설정
            - IpProtocol: tcp
              FromPort: 22
              ToPort: 22
              SourceSecurityGroupId:
                Fn::ImportValue: !Sub ${EnvName}-sg-eic # EC2 인스턴스 연결 엔드포인트 접속만 허용
</code></pre>
</li>

<h2>4.3 세션 관리자 이용한 콘솔에서의 접속</h2>
<p>퍼블릭 서브넷에 NAT 게이트웨이를 생성하고, EC2 인스턴스에서는 세션 관리자를 사용할 수 있는 권한을 부여한다.</p>
<ul>
<li>세션 관리자
<ul>
<li>AWS 시스템 관리자라는 AWS 내 리소스 구성 및 변경 관리, 파라미터 중앙 집중식 관리와 같은 다양한 관리 시스템 기능이 집합된 서비스 내에서 운영되는 서비스</li>
<li>EC2 인스턴스로의 접속을 도와주는 서비스</li>
</ul>
</li>
</ul>
<p>

<img width="1081" height="485" alt="Image" src="https://github.com/user-attachments/assets/c7ea83e7-7cf8-4f25-ac99-b3951cbb5ba0" />

</p>
<ul>
<li>세션 관리자를 사용하려면 EC2 인스턴스에 권한 부여</li>
</ul>
<blockquote>
<p>세션 관리자를 이용할 때 별도의  보안 그룹 설정(인바운드 규칙)은 필요 없다.</p>
</blockquote>
<p>&lt;생성할 구성&gt;</p>
<p>

<img width="1165" height="477" alt="Image" src="https://github.com/user-attachments/assets/2f9b581d-6ce0-405e-9452-66904f7a3b94" />

</p>
<ol>
<li>
<p>세션 관리자를 사용하기 위해 IAM 역할 생성</p>
<pre><code class="language-yaml">	EC2IAMRole:
    Type: AWS::IAM::Role
    DeletionPolicy: Delete # 클라우드포메이션으로 생성한 스택 삭제 시 리소스 같이 삭제
												   # Retaion : 유지
    Properties:
      RoleName: !Sub ${SystemName}-${EnvName}-ec2-role
</code></pre>
</li>
<li>
<p>세션 관리자를 사용하기 위한 정책을 IAM 역할에 추가</p>
<pre><code class="language-yaml">			AssumeRolePolicyDocument: # IAM 역할에 추가할 정책 설정
        Version: &quot;2012-10-17&quot;
        Statement: 
          - Effect: &quot;Allow&quot;
            Principal: 
              Service: 
                - &quot;ec2.amazonaws.com&quot; # EC2 서비스가 이 역할을 가져갈 수 있도록 설정
            Action: 
              - &quot;sts:AssumeRole&quot; # 역할을 수락(Assume)하기 위해 필요한 보안 토큰 서비스(STS) 액션
      Path: &quot;/&quot;
      ManagedPolicyArns: 
      # 세션 관리자 접속을 도와주는 AmazonSSMManagedInstanceCore 정책 추가
        - &quot;arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore&quot;
</code></pre>
</li>
<li>
<p>IAM 역할을 EC2 인스턴스에 연결할 IAM 인스턴스 프로파일 설정</p>
<ul>
<li>
<p>인스턴스 프로파일 : EC2 인스턴스에 IAM 역할을 전달하는 역할</p>
<ul>
<li>AWS 콘솔에서는 생성할 때 자동으로 IAM 역할과 같은 이름으로 인스턴스 프로파일 생성</li>
<li>클라우드포메이션에서는 수동 생성 필요</li>
</ul>
<pre><code class="language-yaml">  EC2InstanceProfile:
    Type: AWS::IAM::InstanceProfile
    Properties:
      InstanceProfileName: !Sub ${SystemName}-${EnvName}-ec2-role
      Path: &quot;/&quot;
      Roles:
        - Ref: EC2IAMRole
</code></pre>
</li>
</ul>
</li>
<li>
<p>EC2 인스턴스에 IAM 역할을 추가하여 세션 관리자를 활성화</p>
<pre><code class="language-yaml">		IamInstanceProfile: 
        Fn::ImportValue: !Sub ${EnvName}-ec2-role
</code></pre>
</li>
<li>

</li>
<li>
<p>세션 관리자 접속을 위해 IAM에 AmazonSSMManagedInstanceCore 정책이 추가되어 있음</p>

<li>

<h2>4.4 세션 관리자 이용한 포트 포워딩 접속</h2>
<p>인터넷에서 접속을 시도하는 패턴을 제외하고는 AWS 관리 콘솔을 이용해 접속할 수 밖에 없었다.</p>
<p>하지만 포트 포워딩을 이용한다면 로컬 PC에서 EC2 인스턴스로 접속할 수 있다.</p>
<p>

<img width="1178" height="573" alt="Image" src="https://github.com/user-attachments/assets/71093950-cdd1-493e-8db8-3a00352e31c1" />

</p>
<ul>
<li>로컬 PC에서 포트 포워딩 세션을 생성하려면 AWS CLI를 이용해야 함</li>
</ul>
<ol>
<li>
<p>자격 증명 호출</p>
<pre><code class="language-powershell">aws sts get-caller-identity
</code></pre>
</li>
<li>
<p>AWS CLI를 이용해 세션을 생성하고 포트 포워딩 실시</p>
<pre><code class="language-powershell">aws ssm start-session --target i-09623d3f85fd0ab27 --document-name AWS-StartPortForwardingSession --parameters &quot;portNumber=22, localPortNumber=8080&quot; Amazon Linux 2
</code></pre>
<ul>
<li><code>aws ssm start-session</code> : 포트 포워딩을 위한 세셩 생성</li>
<li><code>-target</code>: 접속하고자 하는 EC2 인스턴스 ID 입력</li>
<li><code>portNumber</code> : EC2 인스턴스 접속 시 사용하는 포트 번호 지정
<ul>
<li>리눅스 22번, 윈도우 3389번</li>
</ul>
</li>
<li><code>localPortNumber</code> : 로컬 PC에서 사용할 포트 번호 지정</li>
</ul>
<p>

<img width="442" height="126" alt="Image" src="https://github.com/user-attachments/assets/b5cd1ee5-10f0-47e0-a5e3-dde3fc209a11" />

</p>
<p>→ SessionManagerPlugin을 설치 후 명령어를 입력해줘야 한다.</p>
</li>
<li>
<p>테라텀에서 호스트에 localhost, 포트에 8080 입력</p>
<p>

<img width="778" height="438" alt="Image" src="https://github.com/user-attachments/assets/20e966de-2274-441e-84ae-f4ce8fe1da4e" />

</p>
</li>
<li>
<p>사용자 이름 (ec2-user) 입력, 키 페어 선택하여 연결</p>
<ul>
<li>키 페어는 AWS Systems Manager&gt; 파라미터 스토어에서 확인하여 저장</li>
</ul>
</li>
</ol>
